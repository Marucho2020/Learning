# Model Latency vs Throughput Trade-off

	Điểm quan trọng nhất:
		Latency = một request mất bao lâu để hoàn thành.
		Throughput = hệ thống xử lý được bao nhiêu workload trong một đơn vị thời gian.

	Hai thứ này liên quan nhưng không đồng nghĩa. Tối ưu một cái chưa chắc tối ưu cái kia.


# Latency

	Latency trả lời:
		“Một user phải chờ bao lâu?”

	Ví dụ:

		User
		  ↓
		API
		  ↓
		Bedrock
		  ↓
		Model
		  ↓
		Response

		Request bắt đầu: 10:00:00.000
		Response hoàn thành: 10:00:01.200

		Latency = 1.2 giây

				
Trong GenAI, cần đặc biệt phân biệt:
	Time to First Token (TTFT): thời gian từ lúc gửi request đến token đầu tiên.
	Time Per Output Token (TPOT): thời gian để sinh từng token tiếp theo.
	End-to-End Latency: toàn bộ thời gian user nhận được response hoàn chỉnh.		
			
		
	Vì vậy:		
		
Request
   │
   ├── Network / queue
   ├── Model processing
   ├── First token
   │
   ├── token 1
   ├── token 2
   ├── token 3
   └── ...		
		
		
	Một chatbot có thể có:		
		
	TTFT = 300 ms
		Total response = 4 seconds	
			
	User sẽ thấy response bắt đầu rất nhanh, dù tổng thời gian để hoàn thành câu trả lời vẫn là 4 giây.
	Đây là lý do streaming cực kỳ quan trọng đối với perceived latency.			
			
		

# 		2. Throughput là gì?
		
	Throughput trả lời:
		“Trong một khoảng thời gian, hệ thống xử lý được bao nhiêu workload?”	
				
				
	Ví dụ:

	100 requests / second
	hoặc trong GenAI:
	500,000 tokens / minute

	hoặc:
	10,000 requests / minute		
			
			
	Điểm rất quan trọng:

	Throughput không nhất thiết đo bằng requests.
	Đối với LLM, token thường quan trọng hơn request.

	Ví dụ:
	System A		
			
			
	100 requests/minute
		mỗi request = 100 tokens
		→ 10,000 tokens/minute		
			
		
		
	System B
		100 requests/minute
		mỗi request = 10,000 tokens
		→ 1,000,000 tokens/minute

	Hai hệ thống đều có:
	100 requests/minute

	nhưng workload hoàn toàn khác nhau.
			
		
	Vì vậy khi đề AWS nói:
	token throughput

	hãy nghĩ ngay:
	khả năng xử lý/generate token trong một khoảng thời gian		
			
			
		
# 3. Một công thức cực kỳ quan trọng		
		
	Trong hệ thống xử lý request:	
		
		
Throughput = 	Concurrency​	 / Latency
		
		
		
	Ví dụ:
		Concurrency = 100 requests
		Latency = 1 second

	Throughput ≈ 100 requests/sec		
			
		
		
	Nếu:
		Concurrency = 100
		Latency = 2 seconds

	Throughput ≈ 50 requests/sec	
			
			
	Tức là nếu cùng một số lượng worker/concurrent slots, latency tăng thì throughput giảm.
	Nhưng phải cẩn thận:
		Công thức trên là trực giác về hệ thống/concurrency, không phải công thức định nghĩa throughput của mọi LLM service.


	Trong thực tế còn có:

		batching
		queueing
		concurrency limits
		model capacity
		token generation speed
		input/output token size
		throttling
		network
		scheduling


# 5. Trong GenAI còn phức tạp hơn

LLM không giống API CRUD thông thường.
Ví dụ:

	Input:
	10,000 tokens

	Output:
	2,000 tokens

	Input:
	10,000 tokens

	Output:
	2,000 tokens

		Model phải xử lý context lớn và generate output.

		Nếu bạn yêu cầu:
		max_tokens = 8,000

		thì response có thể mất nhiều thời gian hơn so với:
		max_tokens = 500

		Do đó:
		Output token length có ảnh hưởng trực tiếp đến generation latency.
		Đây là một optimization rất thực tế.



# 6. Latency vs Throughput trong Amazon Bedrock

	Amazon Bedrock cung cấp nhiều cơ chế để xử lý workload khác nhau.
	Một trong những cơ chế quan trọng nhất là:

	## Provisioned Throughput
		Provisioned Throughput cung cấp dedicated throughput cho model với model units và thời gian được chỉ định. AWS mô tả model unit dựa trên tổng số input/output tokens mà model unit có thể xử lý/generate trong một phút.



	Nói đơn giản:
		On-Demand

		User
		 ↓
		Bedrock shared capacity
		 ↓
		Model

	Trong khi:
		Provisioned Throughput

		User
		 ↓
		Bedrock
		 ↓
		Dedicated model capacity
		 ↓
		Model
