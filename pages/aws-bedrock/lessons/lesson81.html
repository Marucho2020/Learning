# Agent Handoff — Bản chất, kiến trúc và cách vận hành

Agent Handoff là một trong những khái niệm quan trọng nhất khi thiết kế Multi-Agent System.

Nếu Agent Planning trả lời câu hỏi:

> Tôi cần làm những bước nào để hoàn thành nhiệm vụ?

Thì Agent Handoff trả lời:

> Khi nào tôi nên chuyển quyền điều khiển cho một Agent khác, chuyển cho ai, chuyển thông tin gì và ai chịu trách nhiệm tiếp tục công việc?

Điểm quan trọng nhất: Handoff không đơn thuần là Agent A gọi Agent B. Handoff là chuyển quyền điều khiển (control transfer) giữa các Agent.

# PHẦN I — GIẢI THÍCH TIẾNG VIỆT

## 1. Bản chất của Agent Handoff

Hãy tưởng tượng một công ty phần mềm.

Khách hàng yêu cầu:

"Tôi muốn xây dựng một hệ thống thương mại điện tử."

Có một PM (Supervisor Agent) tiếp nhận yêu cầu.

PM nhận thấy cần ba chuyên môn:

- Backend: thiết kế API, database.
- Security: đánh giá bảo mật.
- Infrastructure: thiết kế AWS infrastructure.

PM giao việc cho từng nhóm trưởng.

Nhưng có hai cách tổ chức công việc hoàn toàn khác nhau.

### Cách A — Delegation (Ủy quyền)

PM giao nhiệm vụ cho Backend Leader.

Backend Leader thực hiện, sau đó trả kết quả về PM.

PM vẫn là người điều phối chính.

Khách hàng hỏi về bảo mật.

Khác biệt cốt lõi:

| Tiêu chí           | Delegation              | Handoff                   |
| ------------------ | ----------------------- | ------------------------- |

## 2. Handoff thực sự chuyển những gì?

Đây là phần rất quan trọng khi triển khai production.

Một handoff đúng nghĩa cần xem xét ít nhất năm thành phần:

| Thành phần        | Ý nghĩa                            |
| ----------------- | ---------------------------------- |
| Control           | Ai có quyền điều khiển tiếp theo?  |
| Context           | Thông tin nào cần chuyển?          |
| Task              | Agent mới phải giải quyết việc gì? |
| State             | Công việc đang ở trạng thái nào?   |
| Identity / Policy | Agent mới được phép làm gì?        |

Ví dụ:

Supervisor chuyển sang Security Agent:

```
{
  "handoff": {
    "from": "supervisor",
    "to": "security-agent",
    "task": "Review the proposed AWS architecture",
    "context": {
      "architecture": "API Gateway + Lambda + DynamoDB",
      "requirements": [
        "Protect customer PII",
        "Support cross-account access"
      ]
    },
    "state": {
      "backend_design": "completed",
      "security_review": "pending"
    }
  }
}
```

Đây là payload minh họa, không phải schema chuẩn bắt buộc của AgentCore.

Một lỗi thường gặp là chỉ chuyển câu hỏi mà không chuyển context.

Ví dụ:

```
Supervisor → Security Agent

"Please review security."
```

Security Agent không biết:

- Kiến trúc nào cần review?
- Yêu cầu bảo mật là gì?
- Những quyết định nào đã được đưa ra?
- Những phần nào đã hoàn thành?

Kết quả là Agent phải hỏi lại hoặc tự suy đoán. Đây là nguyên nhân gây tăng latency, token cost và hallucination.

- IAM least privilege.
- KMS encryption.
- Network isolation.
- Data protection.

Sau đó trả kết quả về workflow theo cơ chế điều phối đã thiết kế.

Bước 5 — Finance Agent

Một workflow có thể tiếp tục chuyển sang Finance Agent để đánh giá chi phí.

Bước 6 — Supervisor tổng hợp

Supervisor nhận kết quả của các domain và tạo báo cáo cuối cùng.

Điểm cần chú ý: Không phải mọi hệ thống handoff đều tự động quay về Supervisor. Việc quay về, kết thúc hoặc chuyển tiếp phụ thuộc vào orchestration model.

## 4. Nested Handoff — Handoff nhiều tầng

Đây là câu hỏi rất đáng quan tâm khi xây dựng hệ thống lớn:

Một Specialist Agent có thể tiếp tục handoff cho Agent khác không?

Có. Không có giới hạn kiến trúc bắt buộc chỉ được ba tầng.

Ví dụ:

```
Supervisor
    |
    v
Backend Agent
    |
    +----> Database Agent
    |          |
    |          +----> SQL Optimization Agent
    |          |
    |          +----> Data Modeling Agent
    |
    +----> API Agent
    |          |
    |          +----> API Security Agent
    |
    +----> Testing Agent
               |
               +----> Performance Testing Agent
```

Backend Agent không cần tự thực hiện tất cả.

Nó có thể đóng vai trò như một Sub-supervisor.

Đây chính là hierarchical multi-agent architecture.

Tuy nhiên, cần phân biệt hai trường hợp:

- Hierarchical delegation: Agent cha vẫn kiểm soát workflow và nhận kết quả từ Agent con.
- Nested handoff: Agent nhận quyền điều khiển có thể tiếp tục chuyển quyền điều khiển cho Agent khác.

Không nên tạo quá nhiều tầng chỉ vì có thể.

Mỗi tầng mới có thể làm tăng:

- End-to-end latency.
- Token consumption.
- Context propagation complexity.
- Failure propagation.
- Khó khăn trong debugging và observability.

Một thiết kế production tốt thường ưu tiên cấu trúc nông, chỉ phân cấp sâu khi có ranh giới domain hoặc ownership thực sự cần thiết.

### 5.1. Strands Agents và Handoff

Trong implementation, framework như Strands Agents có thể quản lý logic điều phối Agent.

Ví dụ pseudocode:

```
# Pseudocode: conceptual handoffasync def supervisor(user_request):    if requires_security_review(user_request):        return await security_agent(            task=user_request,            context=current_context        )    return await backend_agent(        task=user_request,        context=current_context    )
```

Đây chỉ là mô phỏng logic. Nó chưa thể hiện đầy đủ control-transfer semantics của một framework.

Một kiến trúc khác có thể sử dụng A2A để Agent giao tiếp qua ranh giới runtime hoặc service.

### 5.2. A2A và Agent Handoff

Đây là hai khái niệm liên quan nhưng không đồng nghĩa.

- Agent Handoff: Pattern chuyển quyền điều khiển.
- A2A (Agent-to-Agent): Protocol hỗ trợ giao tiếp giữa các Agent độc lập.

Ví dụ:

```
Agent A
   |
   | A2A Message / Task
   v
Agent B
   |
   | Execute
   v
Task Result / Artifact
```

A2A đặc biệt hữu ích khi các Agent:

- Được phát triển bởi các team khác nhau.
- Chạy trên runtime khác nhau.
- Có thể sử dụng framework khác nhau.
- Cần giao tiếp qua network boundary.

A2A có task lifecycle, message và artifact. Vì vậy, đừng nhầm một A2A message với một lệnh gọi function thông thường.

### 5.3. MCP có phải Agent Handoff không?

Không.

| MCP                         | A2A                                           |
| --------------------------- | --------------------------------------------- |
| Model Context Protocol      | Agent-to-Agent Protocol                       |
| Agent kết nối tools/context | Agent giao tiếp với Agent                     |
| Tool invocation             | Agent task/message                            |
| Ví dụ: gọi database tool    | Ví dụ: yêu cầu Security Agent audit kiến trúc |

Ví dụ:

```
Supervisor
    |
    +---- MCP ----> DynamoDB Tool
    |
    +---- A2A ----> Security Agent
```

Đây là cách phân biệt rất quan trọng trong thiết kế Agentic AI.

## 6. Những vấn đề Production phải giải quyết

Đây là phần nhiều người hiểu được handoff nhưng chưa đủ khả năng thiết kế production.

### 6.1. Context Propagation

Agent nhận handoff phải nhận đủ context để tiếp tục công việc.

Nhưng không nên chuyển toàn bộ lịch sử hội thoại một cách máy móc.

Nên thiết kế context contract:

```
{
  "task_id": "task-123",
  "parent_task_id": "task-100",
  "source_agent": "backend-agent",
  "target_agent": "security-agent",
  "objective": "Review IAM configuration",
  "input": {
    "architecture_summary": "...",
    "relevant_findings": ["..."]
  },
  "constraints": {
    "read_only": true,
    "deadline_seconds": 30
  },
  "correlation_id": "request-456"
}
```

Các trường này là ví dụ thiết kế, không phải schema bắt buộc.

Tại sao cần `correlation_id`?

Giả sử một user request tạo ra 20 handoff.

Khi Agent thứ 15 gặp lỗi, hệ thống phải truy ngược được:

- Nó thuộc user request nào?
- Được gọi bởi Agent nào?
- Nằm trong workflow nào?
- Các bước trước đó đã làm gì?

Correlation ID giúp liên kết các trace và log của cùng một workflow.

### 6.2. Shared State và Session

Giả sử Agent A và Agent B chạy trên hai Runtime khác nhau.

Không nên giả định chúng tự động chia sẻ RAM hoặc local filesystem.

```
Agent A (Runtime A)
       |
       | Write
       v
 Shared State Store
       ^
       | Read
       |
Agent B (Runtime B)
```

Có thể sử dụng:

- DynamoDB: state, task metadata, coordination.
- Aurora PostgreSQL: relational data, transactional requirements.
- S3: artifacts, documents, large outputs.
- AgentCore Memory: thông tin memory cần duy trì và truy xuất.

Cần phân biệt:

Memory không phải Transactional State.

Ví dụ:

- "User thích câu trả lời tiếng Nhật" → Memory.
- "Đơn hàng 123 đang ở trạng thái PAYMENT_PENDING" → Transactional State.

Không nên dùng semantic memory làm nguồn dữ liệu có tính nhất quán nghiệp vụ.

### 6.3. Handoff Loop — Vòng lặp vô hạn

Một lỗi nghiêm trọng:

```
Agent A
   |
   v
Agent B
   |
   v
Agent A
   |
   v
Agent B
   |
   v
...
```

Nguyên nhân có thể là:

- Agent không hiểu rõ ownership.
- Routing condition không đủ chính xác.
- Agent không có stopping condition.
- Không có giới hạn số lần handoff.

Giải pháp:

| Cơ chế            | Mục đích                        |
| ----------------- | ------------------------------- |
| Max handoff depth | Giới hạn độ sâu                 |
| Max handoff count | Giới hạn tổng số lần            |
| Timeout           | Giới hạn thời gian              |
| Circuit breaker   | Ngăn gọi tiếp khi service lỗi   |
| Ownership rule    | Xác định Agent chịu trách nhiệm |
| Idempotency key   | Chống thực hiện trùng thao tác  |

Một lưu ý quan trọng: Idempotency không tự ngăn vòng lặp. Nó giúp kiểm soát tác động của những lần thực thi lặp lại.

### 6.4. Security Boundary

Giả sử Security Agent nhận được handoff từ Backend Agent.

Có nên mặc định Security Agent được sử dụng tất cả quyền của Backend Agent không?

Không.

Agent nhận handoff phải được xác thực và cấp quyền theo identity, role và policy của chính nó.

Ví dụ:

```
Backend Agent
   |
   | Handoff
   v
Security Agent
   |
   | IAM authorization
   v
Read-only Security Resources
```

Không nên mặc định chuyển tiếp toàn bộ credentials hoặc quyền của Agent nguồn.

Cần phân biệt:

- Identity: Ai đang thực hiện hành động?
- Authentication: Xác minh danh tính.
- Authorization: Có quyền thực hiện hành động đó không?

Nếu Agent A có quyền ghi database nhưng Agent B chỉ được đọc, handoff không được phép làm Agent B thừa hưởng quyền ghi của A.

### 6.5. Failure Handling

Điều gì xảy ra nếu Agent nhận handoff bị timeout?

Không phải cứ retry là đúng.

Cần phân biệt:

| Lỗi                       | Xử lý                          |
| ------------------------- | ------------------------------ |
| Temporary network failure | Retry có backoff               |
| Throttling                | Exponential backoff + jitter   |
| Invalid context           | Reject / sửa payload           |
| Unauthorized              | Không retry mù quáng           |
| Agent unavailable         | Fallback hoặc báo lỗi          |
| Partial execution         | Kiểm tra state trước khi retry |

Đặc biệt, nếu Agent đã thực hiện một giao dịch nhưng response bị mất, retry có thể gây duplicate transaction.

Đây là lý do production workflow cần task state, idempotency và reconciliation.

## 7. Trade-off của Agent Handoff

| Tiêu chí        | Ưu điểm                           | Chi phí / rủi ro              |
| --------------- | --------------------------------- | ----------------------------- |
| Accuracy        | Chuyên môn hóa theo domain        | Context loss                  |
| Scalability     | Agent độc lập                     | Network overhead              |
| Latency         | Chuyển tới Agent phù hợp          | Nhiều round trips             |
| Cost            | Có thể chọn model nhỏ theo domain | Nhiều lần inference           |
| Maintainability | Tách domain ownership             | Tăng orchestration complexity |
| Security        | Phân quyền riêng từng Agent       | Tăng số trust boundary        |

Quan điểm thiết kế: Không nên tạo nhiều Agent chỉ để làm kiến trúc trông có vẻ thông minh.

Nếu một function hoặc một workflow deterministic giải quyết được vấn đề, hãy dùng nó.

Agent Handoff chỉ thực sự đáng giá khi cần chuyển quyền điều khiển giữa các domain có trách nhiệm, context và quyền hạn khác nhau.

| Shared context            | Context propagation            |

| Tool integration          | MCP / Gateway                  |
| Persistent session state  | State store                    |
| Agent identity            | AgentCore Identity             |
| Prevent recursive calls   | Handoff depth / loop control   |
| Distributed tracing       | Observability / correlation ID |

## 9. Exam Traps

Trap 1: Agent A gọi Agent B tức là Handoff.

Sai. Gọi một tool hoặc API để lấy kết quả không nhất thiết là chuyển quyền điều khiển. Phải xét control-flow semantics.

Trap 2: Dùng MCP để giao tiếp giữa mọi Agent.

Sai. MCP chủ yếu chuẩn hóa việc kết nối với tools và context. A2A phù hợp hơn khi cần giao tiếp giữa các Agent độc lập.

Trap 3: Tất cả Agent dùng chung một session memory là đủ.

Sai. Session, persistent state và semantic memory là các khái niệm khác nhau.

Trap 4: Chuyển toàn bộ conversation history là tốt nhất.

Sai. Có thể tăng token cost, latency và rò rỉ thông tin không cần thiết. Hãy chuyển context tối thiểu nhưng đầy đủ.

Trap 5: Agent nhận handoff kế thừa quyền của Agent gửi.

Sai. Authorization phải được thực hiện theo identity và policy phù hợp.

Trap 6: Dùng Step Functions để thay thế toàn bộ agent reasoning.

Sai. Step Functions phù hợp với workflow có trạng thái và các bước deterministic. Agent framework chịu trách nhiệm reasoning và quyết định hành động động. Hai thành phần có thể phối hợp.

## 10. Scenario Professional-Level

Exam simulation

Một doanh nghiệp xây dựng hệ thống AI phân tích kiến trúc AWS.

Yêu cầu:

- Supervisor Agent tiếp nhận request.
- Backend Agent đánh giá API và database.
- Security Agent thực hiện security audit.
- Cost Agent tính toán chi phí.
- Các Agent chạy trên các AgentCore Runtime độc lập.
- Security Agent có quyền đọc security configuration nhưng không được phép sửa đổi.
- Backend Agent có thể chuyển một phần công việc cho Database Specialist.
- Hệ thống phải theo dõi được toàn bộ execution và tránh lặp handoff vô hạn.

Doanh nghiệp muốn giảm coupling giữa các Agent và cho phép các team phát triển Agent bằng framework khác nhau.

Phương án nào phù hợp nhất?

Chọn một đáp án

A.

&#x20;Dùng một AgentCore Runtime duy nhất, chia các Agent thành các function bên trong và sử dụng chung toàn bộ IAM permissions.

B.

&#x20;Triển khai Agent độc lập trên AgentCore Runtime, sử dụng A2A cho giao tiếp Agent-to-Agent, truyền context/task metadata rõ ràng, áp dụng identity và authorization riêng, đồng thời giới hạn handoff và thiết lập distributed tracing.

C.

&#x20;Sử dụng MCP cho toàn bộ giao tiếp giữa các Agent, chia sẻ một conversation history và một IAM role để giảm độ phức tạp.

D.

### Cách AWS ra đề

Đừng chỉ nhìn thấy từ "multiple agents" rồi chọn A2A.

Hãy tìm các hidden requirements:

1. Independent Runtime: Agent có boundary thực thi riêng.
2. Different frameworks: Cần giao tiếp qua protocol trung lập.
3. Different permissions: Cần identity và authorization độc lập.
4. Nested handoff: Backend có thể tiếp tục chuyển cho Database Specialist.
5. No infinite loops: Cần giới hạn vòng lặp.
6. End-to-end tracing: Cần correlation và observability.

Điều quan trọng là chọn phương án giải quyết đồng thời các constraint, không phải phương án chỉ có thể thực hiện handoff.
