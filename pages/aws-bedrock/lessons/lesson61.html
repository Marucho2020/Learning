Lesson 62 -- AIP-C01 --=Multi-Knowledge-Base Architecture -//


# 1. Bản chất

Giả sử doanh nghiệp có:
	KB-1: HR documents
	KB-2: Finance documents
	KB-3: Engineering documents
	KB-4: Customer manuals
	KB-5: Project progress reports


Một cách rất dễ nghĩ là:

                 User
                   │
                   ▼
             One Knowledge Base
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
       HR       Finance    Engineering

	Nhưng đây không phải lúc nào cũng là kiến trúc tốt.
	
	Multi-Knowledge-Base Architecture nghĩa là:

                         User
                           │
                           ▼
                    Query / Intent
                           │
                           ▼
                    Retrieval Router
                    /       |       \
                   /        |        \
                  ▼         ▼         ▼
               HR KB    Finance KB   Engineering KB
                  │         │            │
                  ▼         ▼            ▼
               Search     Search       Search
                  │         │            │
                  └─────────┼────────────┘
                            ▼
                       Reranking
                            │
                            ▼
                       LLM Response

	Điểm quan trọng nhất:
		Multi-KB không phải mục đích. Nó là một architectural decision để kiểm soát data boundary, security boundary, retrieval quality, lifecycle và operational boundary.




# 2. Tại sao không nhét tất cả vào một KB?

	Ví dụ:

Company
│
├── HR
│   ├── salary
│   ├── benefits
│   └── employee rules
│
├── Finance
│   ├── accounting
│   └── budgets
│
└── Engineering
    ├── architecture
    ├── source documentation
    └── incident reports


	Nếu gom tất cả:
		S3
		 ↓
		One Knowledge Base
		 ↓
		Vector Store

	thì có 4 vấn đề lớn.



	## ① Security boundary
	
		HR có thể chứa:
			salary
			personal information
			employee evaluation


	Engineering employee không nhất thiết được phép truy cập.
	Nếu tất cả nằm chung một KB, bạn phải phụ thuộc nhiều hơn vào:

	metadata filtering
	IAM/application authorization


	Đây là một điểm cực kỳ quan trọng:
		Metadata filtering không phải lúc nào cũng thay thế được data isolation.
		Nếu dữ liệu có security boundary mạnh, tách KB có thể đơn giản và an toàn hơn.




	## ② Retrieval quality

	Query:
		「今年度の営業利益率は？」

	Nếu một vector index chứa:
		Finance
		HR
		Engineering
		Customer support
		Technical documents

		thì semantic search có thể retrieve những document không liên quan.

	Ví dụ:
		Query
		 ↓
		"営業利益率"
		 ↓
		Top 20
		 ├─ Finance report       ← relevant
		 ├─ Sales report         ← relevant
		 ├─ Engineering KPI      ← partially relevant
		 ├─ HR performance KPI   ← irrelevant
		 └─ Project report       ← irrelevant
			
	Sau đó mới rerank/filter.
	Trong nhiều trường hợp, tốt hơn là:

		Query
		 ↓
		Intent = Finance
		 ↓
		Finance KB
		 ↓
		Retrieve
		
	Search space nhỏ hơn → retrieval precision có thể tốt hơn.


# 3. Multi-KB có nghĩa là Router

	Đây mới là phần quan trọng.

	Không nên thiết kế:
		User
		 ↓
		Search tất cả KB
		 ↓
		LLM tự quyết định
	một cách mặc định.


	Thay vào đó:

User Query
     │
     ▼
Query Classification / Routing
     │
 ┌───┼────┬─────┐
 ▼   ▼    ▼     ▼
HR Finance Eng Customer
 │    │    │      │
 ▼    ▼    ▼      ▼
 KB   KB   KB     KB

	Router có thể dựa trên:
	
	## Rule-based routing

		"salary"
		"vacation"
		"employee"
			   ↓
			  HR


		Ưu điểm:
			nhanh
			rẻ
			deterministic

		Nhược:

			khó mở rộng
			query phức tạp khó classify






	## LLM-based routing
		Ví dụ:

	User:
	"Chi phí nhân sự của dự án A trong Q3 là bao nhiêu?"

	LLM Router:

	domain:
	  finance + project

	KB:
	  Finance
	  Project


	Sau đó có thể query nhiều KB.



# 4. Single-KB vs Multi-KB 

| Tiêu chí                    | Single KB     | Multi-KB  |
| --------------------------- | ------------- | --------- |
| Architecture                | đơn giản      | phức tạp  |
| Chi phí vận hành            | thấp          | cao hơn   |
| Security isolation          | yếu hơn       | mạnh hơn  |
| Domain isolation            | thấp          | cao       |
| Retrieval control           | hạn chế hơn   | tốt       |
| Different embedding models  | khó           | dễ        |
| Different chunking strategy | khó           | dễ        |
| Different update frequency  | kém linh hoạt | tốt       |
| Different retention policy  | khó           | tốt       |
| Cross-domain query          | dễ            | phức tạp  |
| Scaling                     | đơn giản      | phức tạp  |
| Governance                  | tập trung     | phân tách |


	Không có đáp án:
		“Multi-KB luôn tốt hơn.”
		AWS rất thích đánh vào điểm này.




# 5. Khi nào nên dùng Multi-KB?
	Tôi sẽ nhớ theo 5 chữ S:


	## 	1. Security

		Dữ liệu có security boundary khác nhau.
		HR ≠ Engineering ≠ Finance



	## 2. Strategy
		Retrieval strategy khác nhau.
		Ví dụ:

		Technical documentation
		→ small chunks

		Legal documents
		→ hierarchical chunks

		Financial reports
		→ table-aware parsing

	Một KB duy nhất sẽ khó tối ưu cho tất cả.	


	## 3. Scale
	Một domain quá lớn.

	Ví dụ:
		Customer support
		10 TB documents

	Trong khi:
		HR
		50 GB

	Tách workload có thể dễ vận hành hơn.



	## 4. SLA
		Các domain có yêu cầu latency/update khác nhau.

		Ví dụ:
			Incident KB
			→ update gần real-time

			Company policy
			→ update vài lần/tháng

		Không nhất thiết phải có cùng ingestion pipeline.




	## 5. Ownership
		Các team khác nhau quản lý dữ liệu.
			HR team
			Finance team
			Engineering team
			Legal team

		Mỗi team có:
			lifecycle
			access policy
			ingestion pipeline
			owner

		riêng.

# 8. Một điểm rất dễ nhầm: Multi-KB ≠ Multi-Vector-Store


	Đây là trap.

	Ví dụ:
		Knowledge Base
			  │
			  ▼
		OpenSearch Serverless
			  │
		 ┌────┼────┐
		 ▼    ▼    ▼
		index1 index2 index3

	Có thể có một KB nhưng nhiều index/data partition, hoặc ngược lại.

	Do đó:

		Knowledge Base là logical abstraction. Vector store/index là retrieval infrastructure.
		Không được đồng nhất hai khái niệm này.

	Đây là bài toán khó hơn.

	User:
		"So sánh chi phí nhân sự của dự án A với ngân sách được phê duyệt."

	Cần:

		Query
		 ↓
		Router
		 ↓
		 ┌─────────────┐
		 │             │
		 ▼             ▼
		Finance KB   Project KB
		 │             │
		 ▼             ▼
		Results      Results
		 │             │
		 └──────┬──────┘
				▼
			Merge Context
				│
				▼
			  Rerank
				│
				▼
			   LLM


Ở đây không nên để LLM tự search vô hạn.

Cần kiểm soát:
	max KBs
	max retrieval calls
	top-K

	token budget

	Nếu không:
		1 query
		 ↓
		5 KB
		 ↓

		 ↓

	latency + cost tăng rất nhanh.




# 10. Multi-KB và Agent
	Bedrock Agent có thể được dùng để quyết định tool/KB nào cần gọi.

User
 ↓
Bedrock Agent
 │
 ├── retrieve_hr()
 │
 ├── retrieve_finance()
 │
 ├── retrieve_project()
 │
 └── calculator()


Đây là agentic retrieval.

Nhưng đừng rơi vào bẫy:
	"Có nhiều KB → dùng Agent."

	Sai.

	Nếu routing đơn giản:
		query contains HR intent
		→ HR KB

	thì Lambda/router deterministic có thể tốt hơn Agent:
		cheaper
		faster
		predictable
		easier to test

	Agent chỉ đáng giá khi workflow có tính động:
		Need HR data?
				↓
		Need project data?
				↓
		Need calculation?
				↓
		Need API?
				↓
		Need human approval?

# 12. Trap quan trọng nhất


Trap 1
	"Một KB luôn tốt hơn vì đơn giản."
		❌ Không đúng.
	
	Đơn giản về infrastructure nhưng có thể phức tạp về:
		authorization
		retrieval quality
		lifecycle
		governance




	Trap 2
		"Multi-KB luôn tốt hơn vì security."
			❌ Không đúng.
			Nếu dữ liệu không có security boundary và domain tương tự nhau, Multi-KB có thể tạo unnecessary complexity.

	Trap 3
		"Metadata filtering giải quyết hoàn toàn authorization."
			❌ Nguy hiểm.
		Authorization nên được enforce ở application/security layer.
		Không nên coi:
		vector metadata filter
		là security boundary duy nhất cho dữ liệu nhạy cảm.

	Trap 4
		"Cross-KB search = search tất cả KB."
		❌ Không nhất thiết.

	Nên:
		query understanding
		→ routing
		→ selective retrieval

	để giảm:
		latency
		cost
		irrelevant context
		
	Trap 5
		"Agent là lựa chọn tốt nhất cho routing."
		❌ Không.
		Nếu workflow deterministic → code/rule-based router thường tốt hơn.
		Agent phù hợp khi cần dynamic tool selection / multi-step reasoning.



# Quy tắc tư duy:
	Security boundary
		  ↓
	Separate KB

	Different retrieval strategy
		  ↓
	Separate KB

	Different lifecycle / ownership
		  ↓
	Separate KB

	Simple homogeneous data

	Single KB

		  ↓

	Dynamic multi-step workflow
