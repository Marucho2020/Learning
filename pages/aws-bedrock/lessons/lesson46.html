# Bản chất:

	Đây là một dịch vụ rất quan trọng đối với AIP-C01, đặc biệt ở phần RAG / Vector Store / Retrieval.

	Amazon OpenSearch Serverless Vector Engine = một vector database/search engine managed bởi AWS, dùng để lưu embedding và tìm các vector gần với vector của query.

# 2. OpenSearch Serverless thực sự lưu cái gì?

	Một record có thể conceptually như:

	{
	  "text": "育児休業は子どもが1歳になるまで取得できます。",
	  "embedding": [0.021, -0.183, 0.442, ...],
	  "department": "HR",
	  "language": "ja",
	  "document_id": "hr-policy-001"
	}


	Trong đó:
		text
		  ↓
		Embedding Model
		  ↓
		[0.021, -0.183, 0.442, ...]
		  ↓
		OpenSearch Vector Engine




	OpenSearch lưu:

		vector
		text
		metadata
		document ID
		các field phục vụ filtering/search

	Điểm rất quan trọng:
		Vector database không chỉ chứa vector.

		OpenSearch Serverless cho phép lưu metadata như number, boolean, date, keyword, geopoint và text cùng với vector. Điều này cực kỳ hữu ích cho metadata filtering trong RAG







# 3. Tại sao dùng OpenSearch thay vì một database bình thường?


	Database SQL truyền thống rất giỏi:
		WHERE department = 'HR'

	hoặc:
		WHERE employee_id = 123

	Nhưng nó không tự nhiên giải quyết câu hỏi:
		"Document nào có ngữ nghĩa gần nhất với câu hỏi này?"



	Vector search làm:

		Query vector
			 ↓
		Similarity Search
			 ↓
		Top-K nearest vectors


	Ví dụ:
		Query:
		"育児休業の申請条件"

			   ↓ embedding

		Q = [0.21, 0.83, -0.14, ...]

		OpenSearch
			Document A = [0.20, 0.81, -0.12, ...]  ← gần
			Document B = [0.71, 0.02,  0.91, ...]  ← xa
			Document C = [0.22, 0.80, -0.10, ...]  ← gần

			   ↓

		A, C được retrieve


	Đây chính là semantic search.
	
	OpenSearch Vector Engine hỗ trợ các distance metric như:
		Euclidean
		Cosine similarity
		Dot product

	và hỗ trợ vector tới 16,000 dimensions.




# 4. k-NN — từ khóa cực kỳ quan trọng
	Vector search của OpenSearch dựa trên k-nearest neighbor (k-NN).

	Ví dụ:
		{
		  "query": {
			"knn": {
			  "embedding": {
				"vector": [0.21, 0.83, -0.14],
				"k": 5
			  }
			}
		  }
		}


	k = 5

	nghĩa là:
		Tìm 5 vector gần nhất với query vector.
		AWS documentation mô tả Vector Engine sử dụng k-NN search và cung cấp k-NN API.





# 5. Vì sao gọi là "Serverless"?

	Đây là phần rất dễ bị đề thi đánh lừa.
	
	Với OpenSearch cluster truyền thống:

		Bạn
		 │
		 ├── chọn instance
		 ├── chọn node
		 ├── cluster size
		 ├── shard
		 ├── replica
		 ├── scaling
		 └── capacity planning



	OpenSearch Serverless:
		Bạn
		 │
		 ▼
		Collection
		 │
		 ▼
		AWS quản lý infrastructure
		 │
		 ├── scaling
		 ├── compute
		 ├── capacity
		 └── underlying infrastructure


# 6. Nhưng "Serverless" KHÔNG có nghĩa là "free"

	Đây là trap rất hay.

		Serverless
		≠
		No infrastructure cost
		
		
	OpenSearch Serverless sử dụng OpenSearch Compute Units — OCUs cho compute capacity.	
		
		
	Vì vậy:

Không phải trả tiền cho EC2 instance trực tiếp không có nghĩa là miễn phí.

Trong bài thi nếu đáp án nói:
	"Use OpenSearch Serverless because it eliminates infrastructure costs" (eliminates loại bỏ )
	→ Sai.

Đúng hơn:
	"Use OpenSearch Serverless to reduce operational overhead and automatically scale capacity."	
		
		
		
		
# 	7. Collection → Index → Document	
		
	Đây là hierarchy phải nhớ.	
		
		
OpenSearch Serverless
        │
        ▼
    Collection
        │
        ├── Index A
        │      ├── Document
        │      ├── Document
        │      └── Document
        │
        └── Index B
               ├── Document
               └── Document		
		
		
		
	Collection
		Logical grouping của một hoặc nhiều indexes.	
		
		
	Index
		Nơi chứa documents có schema tương tự.	
		
		
	Document
		Một record thực tế:		
			{
			  "text": "...",
			  "embedding": [...],
			  "department": "HR"
			}

			AWS định nghĩa collection là logical grouping của một hoặc nhiều indexes.

# 9. OpenSearch Serverless vs Aurora PostgreSQL + pgvector 

|                                 | OpenSearch Serverless         | Aurora PostgreSQL + pgvector      |
| ------------------------------- | ----------------------------- | --------------------------------- |
| Bản chất                        | Search engine / vector search | Relational DB                     |
| Vector search                   | Rất mạnh                      | Có                                |
| Full-text search                | Mạnh                          | Có                                |
| Metadata filtering              | Mạnh                          | Mạnh                              |
| SQL                             | Không phải điểm mạnh          | **Rất mạnh**                      |
| Relational data                 | Không phù hợp bằng Aurora     | **Rất phù hợp**                   |
| Operational overhead            | Thấp                          | Cao hơn                           |
| Serverless                      | Có                            | Có thể dùng Aurora Serverless     |
| RAG                             | Rất phù hợp                   | Rất phù hợp                       |
| Search-centric workload         | **Rất phù hợp**               | Không phải lựa chọn tự nhiên nhất |
| Transaction/relational workload | Không                         | **Phù hợp**                       |



	Rule để thi

	Nếu scenario nói:
		"Application already stores relational business data in PostgreSQL and needs vector search integrated with relational queries."
		→ Aurora PostgreSQL + pgvector có thể là lựa chọn tự nhiên.

	Nếu nói:
		"Need scalable semantic search with minimal infrastructure management."
		→ OpenSearch Serverless Vector Engine.


		
		
#  	10. OpenSearch Serverless vs S3 Vectors

# 11. Filtering — cực kỳ quan trọng trong RAG production		
		
		
	Giả sử công ty có:

		Document A
		department = HR

		Document B
		department = Finance

		Document C
		department = Engineering		
				
		
		
		
	User thuộc HR.

	Query:
		"How many paid vacation days do I have?"

	Nếu chỉ vector similarity:
		Query
		 ↓
		Top-K
		 ↓
		A
		B
		C

		Có nguy cơ lấy nhầm document.

	Ta thêm metadata filtering:		
		Query
		 +
		department = HR
		 ↓
		Vector Search
		 ↓
		HR documents only			
			
			
	Đây là cách kết hợp:
		Semantic similarity + metadata filtering
		OpenSearch Vector Engine hỗ trợ advanced filtering cùng vector search.
		Trong production RAG, đây thường quan trọng hơn việc chỉ tăng k.			
			
			
		
		
# 	12. Trap cực mạnh: tăng Top-K không phải lúc nào cũng tốt
		
	Kết quả:
		Context dài hơn
				↓
		Latency tăng
				↓
		Token cost tăng
				↓
		Nhiễu tăng
				↓
		LLM có thể trả lời kém hơn

	Cho nên:
		More retrieved documents ≠ better RAG.
		Professional exam rất thích trade-off này.		
			
			
			
			
			
			
# 13. NextGen Vector Search — điểm mới cần biết			
			
			
	AWS hiện phân biệt:
		OpenSearch Serverless
		│
		├── NextGen
		│
		└── Classic			
					
			
	NextGen là generation mới và AWS khuyến nghị dùng cho collection mới. NextGen có khả năng scale theo workload và chỉ load các data blocks cần thiết vào memory; workers có thể scale theo nhu cầu CPU/memory.			
				
			
			
	Đừng học theo kiểu cũ:
		"OpenSearch Serverless Vector = Classic"

	Không còn đủ chính xác.			
				
			
			
			
# 	14. Một trap rất thực tế với Bedrock Knowledge Bases	
			
	Nếu bạn tự tạo OpenSearch Serverless vector index để dùng với Bedrock Knowledge Bases, cần chú ý engine/configuration compatibility.

	AWS hiện ghi rõ: với một số filtering/query configuration của Knowledge Bases, vector index trên OpenSearch Serverless cần sử dụng FAISS; nếu index dùng nmslib, có những trường hợp phải tạo index phù hợp khác hoặc để Bedrock tự tạo index.			
				
				
	Đây chính là kiểu chi tiết mà Professional exam có thể dùng để biến:
		"OpenSearch Serverless"

	thành đáp án gần đúng nhưng chưa đủ.

# 17. Cách AWS ra đề


Scenario

Một công ty có 50 triệu tài liệu nội bộ. Ứng dụng GenAI cần semantic search. Team không muốn quản lý cluster hoặc provision infrastructure. Hệ thống cần metadata filtering và vector similarity search.

Các đáp án có thể là:

A. DynamoDB
B. S3
C. OpenSearch Serverless Vector Engine
D. Lambda

→ C.



Nhưng Professional-level sẽ khó hơn:

Company already has PostgreSQL containing customer records and needs vector search combined with complex relational queries.

Lúc này:
	OpenSearch Serverless

nghe rất đúng, nhưng chưa chắc tối ưu.

Có thể:
	Aurora PostgreSQL + pgvector

phù hợp hơn.
