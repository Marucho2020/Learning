# 1. Streaming Response thực chất là gì?

	Streaming Response là cơ chế server gửi kết quả sinh ra từng phần về client ngay khi có, thay vì chờ model tạo xong toàn bộ response rồi mới trả về.


	## Streaming: 
Request
   ↓
LLM xử lý
   ↓
"Amazon"
   ↓
" Bedrock"
   ↓
" is"
   ↓
" a"
   ↓
" fully"
   ↓
" managed..."
   ↓
Client hiển thị liên tục


	Điểm quan trọng:
		Streaming giảm Time To First Token (TTFT) / perceived latency, chứ không nhất thiết giảm thời gian model hoàn thành toàn bộ câu trả lời.


Ví dụ:

	Total generation time = 8 giây

	Non-streaming:
		User chờ 8 giây → nhận kết quả

	Streaming:
		User chờ 1 giây → thấy token đầu tiên
					→ tiếp tục thấy token
					→ 8 giây → hoàn thành



	Vì vậy:
		TTFT ↓
		Perceived latency ↓
		UX ↑
		Nhưng total generation time có thể gần như không đổi

	Đây là một điểm cực kỳ dễ xuất hiện trong câu hỏi Professional-level.

# 3. AWS Bedrock hỗ trợ Streaming như thế nào?

	Trong Amazon Bedrock hiện nay có nhiều API pattern.
	Đối với API inference truyền thống:


| API                             | Behavior                       |
| ------------------------------- | ------------------------------ |
| `InvokeModel`                   | response một lần               |
| `InvokeModelWithResponseStream` | response dạng stream           |
| `Converse`                      | synchronous conversational API |
| `ConverseStream`                | conversational API + streaming |



AWS mô tả InvokeModelWithResponseStream là API trả response theo stream; khả năng streaming của model có thể kiểm tra thông qua responseStreamingSupported.

Đối với conversational application, AWS khuyến nghị Converse / ConverseStream vì cung cấp interface nhất quán giữa các model hỗ trợ messages.

	Mental model:

                Amazon Bedrock Runtime
                       │
          ┌────────────┴────────────┐
          │                         │
     Invoke family             Converse family
          │                         │
     InvokeModel               Converse
          │                         │
 InvokeModelWith            ConverseStream
 ResponseStream



# 4. InvokeModelWithResponseStream

	Đây là API rất quan trọng cần nhớ cho exam.

	Thay vì:
		response = client.invoke_model(...)

	có thể sử dụng:
		response = client.invoke_model_with_response_stream(...)

	Response được trả về thành các event/chunk.
		AWS API reference cho biết operation này yêu cầu permission:


	bedrock:InvokeModelWithResponseStream


và response có thể chứa các chunk hoặc các streaming error như:
	modelStreamErrorException
	modelTimeoutException
	throttlingException
	serviceUnavailableException


	Exam trap

	Nếu câu hỏi nói:
		"The application must stream model responses to users."

	Đáp án:
		InvokeModel
		thường là không đủ.
		
	Bạn phải nghĩ đến:
		InvokeModelWithResponseStream

	hoặc nếu application sử dụng conversational interface:
		ConverseStream




# 5. ConverseStream — cực kỳ quan trọng

	Nếu application là chatbot / multi-turn conversation thì đừng máy móc chọn InvokeModelWithResponseStream.
		ConverseStream cung cấp conversational interface thống nhất và stream response. AWS mô tả ConverseStream là phiên bản streaming của Converse API.


	Mental model:
	
                    Use case
                       │
          ┌────────────┴────────────┐
          │                         │
  Generic model invocation      Conversation
          │                         │
 InvokeModelWithResponseStream  ConverseStream

# 7. Streaming không phải Async Invocation

	Đây là một bẫy rất hay.

		| Cơ chế       | Ý nghĩa                         |
		| ------------ | ------------------------------- |
		| Synchronous  | request → chờ → response        |
		| Streaming    | request → response từng phần    |
		| Asynchronous | request → job → lấy kết quả sau |


	Đừng nhầm:
	
		Streaming
			Request
			  ↓
			Model
			  ↓
			chunk 1
			chunk 2
			chunk 3
			chunk 4


		Async
			Request
			  ↓
			Job ID
			  ↓
			[model processing]
			  ↓
			S3 / result
			  ↓
			retrieve later


			Async phù hợp với workload dài hoặc không cần interactive response.
			Streaming phù hợp với interactive UX.



# 8. Streaming không đồng nghĩa với giảm cost

	Streaming chủ yếu cải thiện:
		TTFT
		Perceived latency
		UX

	Không phải:
		Model quality
		Token generation cost
		Total tokens

	Nếu model vẫn generate:
		Input = 2,000 tokens
		Output = 4,000 tokens

	thì streaming không tự nhiên biến nó thành:
		Input = 2,000
		Output = 3,000

# 10. Lambda + Streaming

Scenario:

	A company has a chatbot using Amazon Bedrock. Users complain that they must wait several seconds before seeing any response. The company wants to improve perceived latency without changing the foundation model.


	Bạn nên suy nghĩ:

		Client
		   ↓
		Streaming-capable API
		   ↓
		Lambda / backend
		   ↓
		Bedrock ConverseStream
		   ↓
		chunks
		   ↓
		Client
		
		
	Điểm cần phân biệt:
		Lambda không làm model generate nhanh hơn.
		Lambda/backend chỉ forward chunks đến client càng sớm càng tốt.
		Nếu backend nhận toàn bộ response rồi mới trả:		
				
		Bedrock
			↓
		wait until complete
		   ↓
		Lambda
		   ↓
		Client

		thì bạn đã phá mất lợi ích của streaming.

# 	12. Guardrails + Streaming — cực kỳ quan trọng		
			
	Đây là phần có thể biến một câu hỏi streaming đơn giản thành câu hỏi khó.
	Khi streaming, bạn không thể đơn giản:			
				
		generate entire response
			   ↓
		scan
			   ↓
		send			
					
			
		vì mục tiêu của streaming là gửi chunk sớm.
		
		
	Amazon Bedrock Guardrails có hai cách xử lý streaming response:			
					
	## 	Synchronous			
		Guardrail buffer một hoặc nhiều chunks, scan trước rồi mới gửi.				
			
		Model
		 ↓
		chunk
		 ↓
		BUFFER
		 ↓
		Guardrail
		 ↓
		safe?
		 ↓
		Client			
			
			
		Ưu điểm:
			an toàn/chính xác hơn vì chunk được kiểm tra trước khi gửi.

		Nhược điểm:
			tăng latency.

		AWS nói synchronous mode tạo thêm latency vì response chunk phải chờ Guardrails scan hoàn thành.			
					
					
					
	## Asynchronous 			
			
	Model
	 ↓
	chunk ───────────────→ Client
	  │
	  └────→ Guardrail scan		
			
				
	Chunk được gửi ngay trong khi Guardrails kiểm tra phía sau.

	Ưu điểm:
		latency thấp hơn.

	Nhược điểm:
		một chunk không phù hợp có thể đã tới client trước khi Guardrails phát hiện.

	AWS cảnh báo asynchronous mode có thể để nội dung không phù hợp xuất hiện trước khi quá trình scan hoàn tất; khi phát hiện, các chunk tiếp theo có thể bị chặn. Ngoài ra, masking sensitive information không được hỗ trợ trong asynchronous mode.			
	


# 13. Bảng trade-off Guardrails + Streaming


|                           | Synchronous      | Asynchronous   |
| ------------------------- | ---------------- | -------------- |
| Response latency          | Cao hơn          | Thấp hơn       |
| Chunk gửi ngay            | Không nhất thiết | Có             |
| Kiểm tra trước khi gửi    | Có               | Không đảm bảo  |
| UX latency                | Tệ hơn           | Tốt hơn        |
| Safety trước khi hiển thị | Tốt hơn          | Có khoảng trễ  |
| Sensitive-data masking    | Hỗ trợ           | Không hỗ trợ   |
| Use case                  | Safety-critical  | Low-latency UX |




# Exam trap cực mạnh

	Scenario:
		The company requires that no unsafe content ever be displayed to the user.

	Đừng chọn:
		Asynchronous guardrail streaming
		chỉ vì nó có latency thấp.

	Nếu requirement là:
		content must be evaluated before being displayed
		→ ưu tiên synchronous processing.

	Ngược lại:
		minimum latency is the highest priority and the company accepts that moderation happens asynchronously
		→ asynchronous có thể phù hợp.

	Đây chính là kiểu trade-off mà AWS thích kiểm tra. 




# 14. Bedrock Agent cũng có Streaming

	Đừng giới hạn streaming chỉ ở model invocation.
	Amazon Bedrock Agent có thể stream final response bằng:
		streamFinalResponse = true


		AWS cho biết mặc định InvokeAgent có thể trả một chunk chứa complete response; bật streaming sẽ chia response thành nhiều chunks, giúp giảm latency trước khi người dùng nhận response đầu tiên.

	Ví dụ:

		User
		 ↓
		Bedrock Agent
		 ↓
		Reasoning / orchestration
		 ↓
		Knowledge Base / Action Group / Tool
		 ↓
		Final response
		 ↓
		chunk 1
		chunk 2
		chunk 3
		 ↓
		User

	
	Đây là một distinction quan trọng:
		Agent streaming ≠ streaming toàn bộ quá trình reasoning.	


	Bạn không nên mặc định rằng user sẽ nhận được:
		Agent thought 1
		Agent thought 2
		Tool decision
		Internal reasoning
		...

	Streaming final response chủ yếu liên quan đến response delivery.



# 15. Agent + Guardrail interval


	Một detail khá dễ thành trap.
		Khi Agent có Guardrail, StreamingConfigurations có thể có:

	applyGuardrailInterval

	AWS dùng interval này để kiểm soát tần suất ApplyGuardrail được gọi trên outgoing response characters. Default interval hiện được document là 50 characters.

	Mental model:

		Generated response:
		"Hello, I am your customer support assistant..."
				↓
		50 chars
				↓
		ApplyGuardrail

		50 chars
				↓
		ApplyGuardrail

		...


	Nếu tăng interval:
		larger interval
			  ↓
		larger chunks
			  ↓
		fewer ApplyGuardrail calls
			  ↓
		potentially lower overhead
		
	Nhưng safety checking trở nên ít granular hơn.	
		
		
		
#	16. Streaming trong RAG
		
	Streaming không chỉ dành cho pure LLM.	
		User
		 ↓
		Bedrock Knowledge Base
		 ↓
		Retrieve documents
		 ↓
		Foundation Model
		 ↓
		Generate answer
		 ↓
		stream response
		 ↓
		User		
				
	Bedrock Knowledge Bases hỗ trợ RetrieveAndGenerateStream, cho phép generated response được trả về theo chunks thay vì đợi toàn bộ response.		
			
	Điểm quan trọng:
		Retrieval không nhất thiết streaming.	
					
		
	Thông thường:
			Retrieve
			 ↓
			documents
			 ↓
			Generate
			 ↓
			stream generated answer

		Nói cách khác, bạn có thể phải chờ retrieval xong trước, nhưng phần generation có thể stream.	
				
		
# 	17. Streaming không giải quyết mọi loại latency	
		
User
 ↓
API
 ↓
Authentication       300ms
 ↓
RAG retrieval        2 sec
 ↓
Prompt construction  500ms
 ↓
LLM TTFT             1 sec
 ↓
Generation           8 sec		
		
		
	Streaming chỉ chủ yếu giúp ở phần:
		LLM generation

	Nếu bottleneck nằm ở:
		RAG retrieval = 2 sec
		thì streaming không biến 2 giây thành 0.

	Đây là tư duy Professional-level:
		Đừng thấy requirement "reduce latency" rồi chọn streaming ngay. Hãy xác định latency budget nằm ở đâu.		
			
			
		
#	18. TTFT vs Total Latency
		
		
Nên phân biệt:
	TTFT — Time To First Token
	
		Thời gian:
			request
			 ↓
			first token		
				
				
	Total response latency			
	Thời gian:
		request
		 ↓
		last token				
						
					
	Ví dụ:
		TTFT = 1.2 sec
		Total = 9 sec					
							
					
	Streaming cải thiện mạnh:
		TTFT

	nhưng không nhất thiết:
		Total = 9 sec → 4 sec				
					
					
Muốn giảm total latency có thể phải xem:
	model selection
	smaller model
	prompt size
	RAG retrieval
	output token limit
	inference configuration
	latency-optimized inference options
	caching
	architecture				
				
				
# 	19. Streaming và model selection		
				
				
	Một model không nhất thiết hỗ trợ streaming.

	AWS cho phép kiểm tra:
		responseStreamingSupported
		thông qua GetFoundationModel.

	Vì vậy scenario:
		The application requires real-time streaming, but the selected foundation model does not support streaming.
		Không thể chỉ sửa frontend.

	Bạn phải:
		select another model
		hoặc thay đổi architecture.

	Trap
		"Amazon Bedrock supports streaming, therefore every foundation model supports streaming."

	Sai.
		Streaming support là thuộc tính cần kiểm tra ở model/API compatibility.

# 23. Scenario kiểu AIP-C01

	Scenario
		Một công ty xây dựng AI customer-support trên Amazon Bedrock.

		2,000 tokens

		8–10 seconds
