# 1. Bản chất: Agent thực sự là gì?	
			
	Nói thẳng:
		Agent không phải là một model. Agent là một runtime system sử dụng model để quyết định và thực hiện hành động qua nhiều bước.			
				
	LLM chỉ đóng vai trò reasoning/decision engine.			
				
				
	User
	  ↓
	Agent Runtime
	  │
	  ├── State / Session
	  ├── Memory
	  ├── Identity
	  ├── Policy / Guardrails
	  ├── LLM
	  │     ↓
	  │   Decision
	  │
	  ├── Tool
	  │     ↓
	  │   Result
	  │
	  ├── Observation
	  │     ↓
	  │   LLM
	  │
	  └── Repeat
			↓
		 Final Response			
				
				
	Điểm quan trọng nhất là:
		Agent có một control loop.

# 4. Thành phần quan trọng nhất: Agent Loop
Đây là thứ bạn cần hiểu ở mức implementation, không chỉ học thuộc.

state = initialize_session()

while not state.is_complete:

    observation = collect_observation(state)

    decision = llm.decide(
        observation=observation,
        tools=available_tools,
        policies=policies
    )

    if decision.requires_tool:

        authorize(decision.tool)

        result = execute_tool(
            decision.tool,
            decision.arguments
        )

        state = update_state(
            state,
            result
        )

    elif decision.requires_human:

        request_human_approval()

    else:

        return decision.final_response




	Đây là abstraction rất quan trọng.

	Agent runtime không đơn giản là:
		llm.invoke()

		LLM
		 ↓
		Decision
		 ↓
		Tool execution
		 ↓
		Observation
		 ↓
		State update
		 ↓
		LLM
		 ↓
		Decision
		 ↓
		...


# 5. Vì sao phải có State?

	Đây là điểm dễ bị hiểu sai.
	LLM bản thân nó không phải application state manager.
	Ví dụ agent đang thực hiện:

		
	Sau bước 1:

	projects = [
		P001,
		P002,
		P003
	]

	Sau bước 2:

	P001 → OK
	P002 → DELAYED
	P003 → OK

	Sau bước 3:

	owner(P002) = Tanaka

	Sau bước 4:

	notification_sent = true

	Runtime cần duy trì state:

	{
	  "task": "...",
	  "projects": ["P001", "P002", "P003"],
	  "delayed": ["P002"],
	  "owner": "Tanaka",
	  "notification_sent": true
	}

	Nếu không có state management, agent rất dễ:
		mất context
		thực hiện lại action
		gửi notification hai lần
		quên tool result
		không resume được sau failure




# 6. Session State ≠ Memory


| Khái niệm          | Mục đích                                      |
| ------------------ | --------------------------------------------- |
| Session state      | trạng thái của task/session hiện tại          |
| Short-term context | thông tin cần cho reasoning hiện tại          |
| Memory             | thông tin được lưu để sử dụng trong tương lai |
| Knowledge Base     | knowledge bên ngoài để retrieval              |
| Database           | system-of-record                              |


Ví dụ:

	Session State
		current_task = "Analyze report"
		step = 3
		tool_result = {...}

	Trong khi Memory:
		User prefers Japanese responses.
		User's department = Engineering.

	Knowledge Base:
		Company policies
		Technical documents
		Manuals

	Database:
		Employee ID
		Project status
		Sales transactions

	Không được gom tất cả thành “memory”.



# 7. Agent Runtime + Identity

	Production Agent bắt buộc phải trả lời câu hỏi:
	Agent đang hành động với quyền của ai?


	Ví dụ:
		User A
		   ↓
		Agent
		   ↓
		Query Salesforce
		   ↓
		What permissions?

	Không thể để agent có:
		AdministratorAccess
		chỉ vì implementation đơn giản.

	Runtime phải kết hợp:

		User identity
			  ↓
		Authentication
			  ↓
		Authorization
			  ↓
		Tool access

	Ví dụ:

		Employee
		  ↓
		Agent
		  ↓
		Salesforce
		  ↓
		Only user's permitted accounts

	Đây là một trong những điểm quan trọng khi học AgentCore Identity.



# 8. Agent Runtime + Policy


	LLM có thể quyết định:
		“Delete this production database.”

	Nhưng:
		LLM decision ≠ authorization

	Runtime phải có policy layer:

		LLM
		 ↓
		"delete_database"
		 ↓
		Policy
		 ↓
		DENY

	Hoặc:

		LLM
		 ↓
		"send_payment"
		 ↓
		Policy
		 ↓
		Human approval required
		 ↓
		Approved
		 ↓
		Execute

	Đây là nguyên tắc production cực kỳ quan trọng:
		Never let model output directly become an unrestricted system action.




# 9. Tool Execution

	Agent cần tool để tác động ra thế giới bên ngoài.

	Ví dụ:

		LLM quyết định:

		{
		  "tool": "get_customer",
		  "arguments": {
			"customer_id": "C001"
		  }
		}

	Runtime chịu trách nhiệm:

		validate arguments
				↓
		authorize
				↓
		execute
				↓
		timeout
				↓
		retry if appropriate
				↓
		capture result
				↓
		return observation

	LLM không nên trực tiếp thực thi tool.


# 10. Tool failure


Đây là nơi Agent khác chatbot rất rõ.

Tool có thể:

timeout
	401
	403
	404
	429
	500
	network error
	invalid response
	partial result

Agent runtime cần xử lý.

Ví dụ:

	LLM
	 ↓
	call API
	 ↓
	HTTP 500
	 ↓
	Runtime
	 ↓
	retry
	 ↓
	success
	 ↓
	LLM

Hoặc:

	HTTP 403
	 ↓
	Do NOT retry blindly
	 ↓
	return authorization failure
	 ↓
	LLM decides alternative


	Exam trap

		Retry tất cả lỗi là sai.

		Retry phù hợp hơn với lỗi transient:
			timeout
				429
				temporary 5xx

		Không nên retry mù quáng:
			401
			403
			invalid request
			business validation error


# 11. Termination Condition


Agent loop phải có điểm dừng.

Nếu không:
	LLM
	 ↓
	tool
	 ↓
	LLM
	 ↓
	tool
	 ↓
	LLM
	 ↓
	...
	=> runaway agent.

Production runtime cần:

	max steps
	max execution time
	max token budget
	max cost
	termination condition

Ví dụ:
	MAX_STEPS = 20

	for step in range(MAX_STEPS):
		...

Hoặc:

	budget exceeded
		  ↓
	terminate

Đây là vấn đề:
	reliability + cost control + security
	chứ không chỉ là performance.

# 14. AgentCore Runtime vs Lambda

	Hai thứ này rất dễ nhầm.

	Lambda
		event
		 ↓
		function
		 ↓
		result

	Lambda thích hợp cho:

		deterministic execution
		stateless function
		event processing
		API backend
		
	Agent Runtime
		goal
		 ↓
		reason
		 ↓
		decision
		 ↓
		tool
		 ↓
		observation
		 ↓
		reason
		 ↓
		...

	Agent runtime phù hợp với:

		non-deterministic reasoning

# 15. Agent Runtime vs Step Functions

	Đây cũng là một câu hỏi Professional-level.
		Step Functions
		Workflow thường được xác định trước:
		A
		 ↓
		B
		 ↓
		C
		 ↓
		D

	Có thể có:
		Choice
		Retry
		Catch
		Parallel
		Map
		Timeout
		Nó phù hợp với deterministic orchestration.



	Agent

		LLM quyết định:
			A?
			B?
			Search first?
			Ask user?
			Call API?
			Try another tool?

		Đây là dynamic orchestration.





|                     | Step Functions            | Agent Runtime   |
| ------------------- | ------------------------- | --------------- |
| Control flow        | predefined                | model-driven    |
| Determinism         | cao                       | thấp hơn        |
| Reasoning           | không phải mục tiêu chính | core capability |
| Tool selection      | workflow designer         | agent/model     |
| Auditability        | rất tốt                   | phức tạp hơn    |
| Cost predictability | cao                       | thấp hơn        |
| Flexibility         | thấp hơn                  | cao             |
| Best use            | business workflow         | adaptive task   |


Kiến trúc production thường không phải chọn một trong hai.

	Có thể:
		Agent
		 ↓
		Step Functions
		 ↓
		Deterministic business process

	Ví dụ:
		Agent
		 ↓
		"Customer wants refund"
		 ↓
		Step Functions
		 ↓
		validate order
		 ↓
		check eligibility
		 ↓
		issue refund
		 ↓
		send confirmation

	Agent quyết định nên làm gì.
	Step Functions đảm bảo quy trình phải được thực hiện như thế nào.
	Đây là một design pattern rất mạnh.

# 18. Cost / Latency trade-off

Agent có một vấn đề rất lớn:

	Một request có thể tạo ra nhiều model calls.

	Chatbot:
		1 request
		→ 1 LLM call

	Agent:
		1 request
		→ LLM
		→ tool
		→ LLM
		→ tool
		→ LLM
		→ tool
		→ LLM

	Nếu mỗi loop mất:
		2 sec

	và có 8 bước:
		≈ 16 sec

	chưa kể:
		network latency
		tool latency
		retrieval
		model queueing

	Cost cũng tăng:
		N × model invocation
		+
		tool execution
		+
		retrieval
		+
		memory
		+
		observability

	Vì vậy production agent phải tối ưu:
		number of steps
		model selection
		context size
		tool latency
		parallel tool calls
		caching
		early termination
