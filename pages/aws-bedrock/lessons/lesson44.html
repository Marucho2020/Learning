# Vector Database — bản chất


Nếu học để thi AIP-C01, đừng hiểu Vector Database đơn giản là “database lưu vector”. Bản chất quan trọng hơn là:
	Vector Database là hệ thống lưu trữ và tìm kiếm các vector theo độ tương đồng (similarity), thay vì chủ yếu tìm kiếm theo giá trị chính xác của từ khóa.

Trong GenAI/RAG, nó giải quyết một bài toán rất cụ thể:
	“Trong hàng triệu đoạn dữ liệu, đoạn nào có ý nghĩa gần với câu hỏi của user nhất?”




# 1. Trước hết: Vector là gì?

	không cần giống nhau về mặt chữ.
	Nhưng embedding của chúng có thể gần nhau về mặt semantic meaning.





# 2. Database thông thường khác Vector Database thế nào?


	## Traditional Database 

		Ví dụ:
			SELECT *
			FROM employees
			WHERE name = 'Tanaka';

		Database đang tìm theo:
			exact value / s	tructured condition

		Ví dụ:
			name = Tanaka
			age > 30
			department = Engineering





	## Vector Database


	User hỏi:
		"Nhân viên có thể nghỉ phép như thế nào?"

	Hệ thống không nhất thiết tìm chính xác chuỗi:
		"nhân viên có thể nghỉ phép như thế nào"

	Mà:

		User Query
			↓
		Embedding Model
			↓
		Query Vector
			↓
		Similarity Search
			↓
		Top-K vectors gần nhất

	Ví dụ:

	Query
	"Nhân viên có thể nghỉ phép như thế nào?"

			↓ embedding

	q = [0.22, -0.71, 0.47, ...]

			↓ similarity search

		Document #182   similarity = 0.94
		Document #923   similarity = 0.91
		Document #431   similarity = 0.87

	Sau đó các document này được đưa vào LLM.
	Đây chính là phần Retrieval trong RAG.





# 3. Vector Database thực chất đang làm gì?


Có thể nhìn nó thành 3 nhiệm vụ:

	1. STORE
	   lưu vector + metadata

	2. INDEX
	   tạo cấu trúc giúp tìm vector gần nhau nhanh

	3. SEARCH
	   tìm Top-K vector gần query vector nhất





	## Ví dụ:
		Vector
			[0.21, -0.73, 0.45, ...]

		Metadata
		{
		  document_id: "doc-123",
		  department: "HR",
		  language: "ja",
		  year: 2026
		}

		Original text
		"社員は入社6ヶ月後から..."


	Một record trong Vector Database thường không chỉ có vector.

	Nó thường có:
		Embedding
		   +
		Original content / document reference
		   +
		Metadata

	Đây là điểm rất quan trọng khi thiết kế RAG.




# 4. Similarity Search là trái tim của Vector Database


	Giả sử query vector:
		Q = [0.8, 0.7]

	Database có:

		A = [0.9, 0.8]
		B = [0.1, 0.2]
		C = [0.75, 0.72]

	Ta muốn tìm:
		distance(Q, A)
		distance(Q, B)
		distance(Q, C)

	Sau đó lấy các vector gần nhất.
	Có nhiều cách đo similarity/distance.
	
	
	
	## Cosine similarity
	
		Rất phổ biến trong embedding search.

	Ý tưởng:

		vector càng cùng hướng
				↓
		semantic similarity càng cao	
			
	
	
	## Euclidean distance
		Đo khoảng cách hình học trực tiếp.


	## Dot product
		Tính tích vô hướng.

# 	5. Exact Search vs Approximate Search
	
	Đây là một trap rất đáng nhớ trong AIP-C01.	
	
	
	Giả sử có:
		100 million vectors	
		
		
	Nếu mỗi query phải tính khoảng cách với:	
		100,000,000 vectors	
	
	
	thì rất chậm.
		Vì vậy Vector Database thường sử dụng Approximate Nearest Neighbor (ANN).	


	Thay vì:
		Search EVERY vector

	nó xây dựng index để nhanh chóng tìm:

		vectors that are VERY LIKELY
		to be the nearest neighbors



	## Trade-off:

	| Cách     | Accuracy |        Latency |  Compute |
	| -------- | -------: | -------------: | -------: |
	| Exact NN | Cao nhất |            Cao |      Cao |
	| ANN      |  Rất cao | Thấp hơn nhiều | Thấp hơn |


Bản chất của ANN:
	Hy sinh một chút tính chính xác tuyệt đối để đổi lấy tốc độ và khả năng scale.
	Đây là tư duy Professional-level: không có giải pháp miễn phí.

# 11. Metadata filtering cực kỳ quan trọng

			similarity : (sự giống nhau)
	Vector similarity không phải lúc nào cũng đủ.

	Ví dụ user hỏi:
		"Chính sách nghỉ phép của nhân viên Nhật Bản năm 2026?"
		
	Vector search có thể tìm:
		
		Japan 2025
		Japan 2026
		Vietnam 2026
		US 2026

	Nhưng ta có metadata:

	{
	  "country": "Japan",
	  "year": 2026,
	  "department": "HR"
	}

	Ta có thể filter trước/sau tùy engine:
		country = Japan
		AND
		year = 2026

	sau đó thực hiện semantic retrieval.
	Đây gọi là metadata filtering / hybrid retrieval strategy.




# 12. Hybrid Search
	Đây là concept cực kỳ quan trọng.


	## Keyword search

		Tìm theo từ:
			"Amazon Bedrock"

		Nếu document chứa chính xác:
			Amazon Bedrock
			→ match tốt.





	## Semantic search

		Tìm theo ý nghĩa.
			"dịch vụ AWS để xây dựng ứng dụng GenAI"

		có thể tìm được:
			Amazon Bedrock
			dù câu hỏi không chứa chính xác chữ đó.



	## Hybrid

	Kết hợp:
		Keyword relevance
				+
		Semantic similarity
				↓
		Combined ranking

	Trong production RAG, hybrid retrieval thường mạnh hơn việc cực đoan chỉ dùng một loại search.



# 13. Một hiểu lầm nguy hiểm: Vector Database không "hiểu" nội dung

	Vector Database không hiểu tiếng Việt, tiếng Nhật hay tiếng Anh theo nghĩa như LLM.


	Nó chỉ nhận:
		Vector A
		Vector B

	và tính:
		A gần B?

	Cái quyết định semantic meaning chủ yếu nằm ở:
		Embedding Model
		
	Nếu embedding model kém với tiếng Nhật:

		Japanese query
			   ↓
		Poor embedding
			   ↓
		Poor vector representation
			   ↓
		Poor retrieval
			   ↓
		LLM gets wrong context
			   ↓
		Bad answer


	Cho nên:
		Vector Database không thể cứu một embedding model tệ.
		Đây là một insight quan trọng khi debug RAG.

# 15. Các tham số retrieval cần nhớ


	Ví dụ:
		Top-K = 5

	nghĩa là:
		lấy 5 kết quả gần nhất.

	Nhưng:
		Top-K càng lớn

	không có nghĩa:
		RAG càng tốt

	Vì context đưa vào LLM tăng:

		K ↑
		→ context ↑
		→ token ↑
		→ cost ↑
		→ latency ↑
		→ noise ↑

	Có thể xảy ra:

		K = 3 → thiếu context
		K = 10 → đủ context
		K = 50 → quá nhiều noise

	Do đó phải tune retrieval, không phải cứ tăng K.

# 17. Vector Database vs Traditional DB — nhớ bằng bản chất

|                | Traditional DB                | Vector DB                |
| -------------- | ----------------------------- | ------------------------ |
| Tìm kiếm chính | Exact / structured            | Similarity               |
| Input          | String, number, date...       | Vector                   |
| Query          | SQL/filter                    | k-NN / ANN               |
| Mục tiêu       | tìm record thỏa điều kiện     | tìm item gần về semantic |
| RAG            | Metadata / transactional data | Semantic retrieval       |
| Index          | B-tree, Hash...               | HNSW, IVF...             |
| Use case       | Orders, users, transactions   | Semantic search, RAG     |
