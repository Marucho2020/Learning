Lesson 54 -- AIP-C01 --=S3 làm nguồn dữ liệu cho RAG -//


Điểm cần nhớ ngay:
	S3 thường là source of truth / landing zone
	S3 không phải Vector Database. S3 chỉ lưu dữ liệu gốc (raw/source documents). Knowledge Base sẽ lấy dữ liệu từ S3 → parse → chunk → embedding → lưu vector vào vector store → phục vụ retrieval.

		Document repository / data source

# 2. Bản chất của S3 trong RAG		
		
| Tầng             | Thành phần   | Nhiệm vụ                           |
| ---------------- | ------------ | ---------------------------------- |
| ① Raw data       | S3           | Lưu tài liệu gốc                   |
| ② Retrieval data | Vector Store | Lưu chunks + embeddings + metadata |
| ③ Generation     | Bedrock FM   | Sinh câu trả lời                   |
	
		
		
	Ví dụ:	
		
PDF 10 MB
        │
        ▼
       S3
        │
        ▼
      Parse
        │
        ▼
  "AWS provides..."
  "Amazon Bedrock..."
  "Knowledge Bases..."
        │
        ▼
     Chunking
        │
        ▼
 chunk1 / chunk2 / chunk3
        │
        ▼
    Embedding
        │
        ▼
 [0.13, -0.82, 0.44, ...]
        │
        ▼
   Vector Store		
		
		
	Điểm cực kỳ quan trọng:
		S3 chứa PDF/DOCX/TXT/HTML...

	Vector store chứa:
		chunk
		embedding
		metadata

	Không nên nghĩ:
		"S3 chứa embedding nên S3 là vector DB."

	Không.
		S3 chỉ là object storage.		
			
		
# 	3. Tại sao AWS thường dùng S3 làm Data Source?	
		
	Vì S3 cực kỳ phù hợp với việc làm document repository.
	Ví dụ doanh nghiệp có 500.000 tài liệu.	
		
	Thay vì:
		Application
		   ↓
		Database

	có thể thiết kế:

		Users / Applications
				↓
			   S3
				↓
		Knowledge Base
				↓
		Vector Store		
				
			
	S3 có các đặc điểm rất phù hợp:
		durable storage
		scalable
		relatively low cost
		versioning
		lifecycle management
		encryption
		IAM integration
		event integration
		folder/prefix organization

	Đặc biệt:
		Tách storage của source documents khỏi retrieval layer.
		Đây là một design principle rất quan trọng.			
			
			
		
		
# 	4. S3 Data Source ≠ Knowledge Base	
		
	Đây là một trap rất dễ gặp.

	Giả sử:
		S3 bucket
			↓
		Knowledge Base

	Không có nghĩa S3 trở thành Knowledge Base.
	
	Knowledge Base thực hiện nhiều bước xử lý:		
		S3
		 ↓
		Ingestion
		 ↓
		Parsing
		 ↓
		Chunking
		 ↓
		Embedding
		 ↓
		Vector Store			
				
	Do đó:

		S3 = nơi dữ liệu sống
		Knowledge Base = hệ thống biến dữ liệu thành dữ liệu có thể retrieval
		Vector Store = nơi phục vụ similarity search				
						
				
		
# 	5. Khi document trong S3 thay đổi thì sao?	
		
		
	Đây là chỗ bắt đầu có tư duy production.

	Ví dụ:
		policy-v1.pdf
		được upload vào S3.

	Knowledge Base ingest:

		policy-v1.pdf
			   ↓
		chunks
			   ↓
		embeddings

	Sau đó công ty sửa document:
		policy-v2.pdf
		S3 đã có dữ liệu mới.

	Nhưng:

		Vector index không tự động có nghĩa là đã phản ánh nội dung mới chỉ vì file trong S3 thay đổi.
		Cần có quá trình synchronization / ingestion để đưa dữ liệu mới vào Knowledge Base/vector store.
		Đây là một điểm cực dễ bị đề thi gài.

# 	7. S3 không chỉ chứa PDF	
		
		
	Một trap khác:
		"RAG source trên S3 = PDF"
		Sai.

	S3 có thể chứa nhiều loại document/data format tùy pipeline/parser hỗ trợ.

	Ví dụ:
		.pdf
		.docx
		.txt
		.md
		.html
		.csv
		...

	Điều quan trọng không phải "S3 chứa loại file gì", mà là:
		Data ingestion pipeline có khả năng parse format đó hay không		
				
				
			
# 8. Metadata trong S3
	Đây là phần rất quan trọng khi học RAG nâng cao.	
		
		
	Giả sử:
		s3://company-kb/

		hr/
		  vacation.pdf

		finance/
		  expense-policy.pdf

		security/
		  password-policy.pdf

	Bạn có thể muốn retrieval có filter:		
			
	department = "HR"

	hoặc:
		document_type = "policy"

	hoặc:
		year = 2026

	Conceptually:

	Document
	   │
	   ├── content
	   │
	   └── metadata
			  ├── department=HR
			  ├── year=2026
			  └── document_type=policy		
			
			
			
	Khi retrieval:
		User query
		   +
		metadata filter
				↓
		Vector Search
				↓
		Relevant chunks

	Điều này giúp giảm:
		search space
		irrelevant retrieval
		hallucination risk
		latency

# 	10. Tại sao không lưu tất cả trực tiếp vào Vector DB?	
		
	Câu này rất đáng suy nghĩ.
		Vector DB không nên được coi là nơi lưu source-of-truth documents.		
			
		
	Ví dụ:
		S3
		 └── original.pdf

	và:

		Vector DB
		 ├── chunk_001
		 ├── chunk_002
		 ├── chunk_003
		 └── embeddings

	Nếu cần:
		re-chunk
		đổi embedding model
		đổi chunking strategy
		rebuild index
		migrate vector DB

	thì source document vẫn nằm nguyên trong S3.

	Bạn có thể:
		S3
		 ↓
		new chunking strategy
		 ↓
		new embedding model
		 ↓
		new vector index

	Đây chính là lý do architecture này có tính reproducibility và maintainability tốt.		
			
			
			
			
# 	11. Đây là tư duy cực quan trọng cho AIP-C01		
			
			
			
Hãy nhớ 3 lớp:

	SOURCE OF TRUTH
		  ↓
		 S3
		  ↓
	RETRIEVAL REPRESENTATION
		  ↓
	Vector Store
		  ↓
	GENERATION
		  ↓
	Foundation Model			
				
				
				
	Đừng trộn chúng với nhau.		
			
| Thành phần      | Vai trò                        |
| --------------- | ------------------------------ |
| S3              | Original documents             |
| Parser          | Hiểu cấu trúc/content document |
| Chunker         | Chia document                  |
| Embedding model | Text → vector                  |
| Vector Store    | Similarity search              |
| Retriever       | Tìm relevant chunks            |
| FM              | Generate answer                |
			
			
			
# 13. Scenario kiểu AWS Professional			
			
	Scenario
		Một công ty lưu 2 triệu tài liệu PDF trong S3. Họ muốn xây dựng hệ thống RAG nội bộ.			
					
						
	Yêu cầu:
		tài liệu gốc phải được lưu lâu dài
		có thể rebuild vector index
		có thể thay đổi embedding model
		giảm operational overhead
		hỗ trợ semantic retrieval			
					
	Architecture hợp lý về mặt nguyên tắc:

                  S3
          Source Documents
                  │
                  ▼
          Bedrock Knowledge Base
                  │
        ┌─────────┴─────────┐
        │                   │
     Parsing             Chunking
        │                   │
        └─────────┬─────────┘
                  ▼
           Embedding Model
                  │
                  ▼
             Vector Store
                  │
                  ▼
             Retrieval
                  │
                  ▼
             Bedrock FM


# Cách suy luận trong phòng thi

	Nếu đề nói:
		authoritative/original/source documents
		→ nghĩ S3

	Nếu nói:
		semantic similarity / nearest neighbors / embeddings
		→ nghĩ Vector Store

	Nếu nói:
		generate natural-language answer
		→ nghĩ Foundation Model

	Nếu nói:
		retrieve relevant information from enterprise documents
		→ nghĩ RAG / Knowledge Base
