# 	1. Nói thẳng: Agent không đơn giản là "Chatbot thông minh hơn"
	
	Agent = hệ thống dùng LLM làm bộ phận ra quyết định để tự xác định và thực hiện các bước cần thiết nhằm đạt một mục tiêu.
		Điểm cốt lõi không phải là "nói chuyện tự nhiên".
	
	
	Mà là:
		LLM không chỉ trả lời → LLM quyết định phải làm gì tiếp theo → sử dụng tool → quan sát kết quả → quyết định bước tiếp theo → cuối cùng mới trả kết quả.	
		
		
	Có thể hình dung:	
	
		Chatbot truyền thống
			User
			 ↓
			Prompt
			 ↓
			LLM
			 ↓
			Answer	
		
	
	Trong khi Agent:
	
		User
		 ↓
		Goal
		 ↓
		┌──────────────────────┐
		│        Agent         │
		│                      │
		│  Understand goal     │
		│       ↓              │
		│  Decide next action  │
		│       ↓              │
		│    Select tool       │
		│       ↓              │
		│   Execute tool       │
		│       ↓              │
		│ Observe result       │
		│       ↓              │
		│ Decide again         │
		│       ↓              │
		│   More tools...?     │
		└──────────────────────┘
		 ↓
		Final answer / action	
			
	Khả năng tự điều phối hành động (reasoning + planning + tool use + iteration) mới là bản chất.		
			
			
# 	2. Chatbot thường thực chất là gì?		
		
	Ví dụ:
		User: "Chính sách nghỉ phép của công ty là gì?"

	Một chatbot RAG:
		User
		 ↓
		Embedding
		 ↓
		Vector Search
		 ↓
		Relevant documents
		 ↓
		LLM
		 ↓
		Answer

	Ví dụ:
		"Nhân viên chính thức được 20 ngày phép/năm."
		Nó không cần quyết định hành động tiếp theo.

	Nó chỉ:
		Input → Process → Output




# 3. Agent thì khác ở đâu?

	Giả sử user nói:
		"Tôi muốn nghỉ phép từ ngày 10 đến ngày 14, hãy kiểm tra xem tôi còn đủ phép không và đăng ký giúp tôi."

	Đây không còn đơn thuần là Q&A.

	Agent có thể phải:
		1. Hiểu yêu cầu
			  ↓
		2. Kiểm tra lịch nghỉ
			  ↓
		3. Kiểm tra số ngày phép còn lại
			  ↓
		4. Tính số ngày nghỉ
			  ↓
		5. Nếu đủ → tạo request
			  ↓
		6. Gửi request
			  ↓
		7. Trả kết quả

	Các bước này có thể cần các tool khác nhau:
		Agent
		 ├── get_employee_info()
		 ├── get_leave_balance()
		 ├── check_calendar()
		 ├── calculate_leave_days()
		 └── submit_leave_request()


	Điểm quan trọng:
		Developer không nhất thiết phải hard-code toàn bộ thứ tự này.

	Agent có thể dựa vào goal + tool descriptions + context để quyết định:
		"Trước tiên tôi cần kiểm tra leave balance."

	Sau đó:
		"Đủ phép. Bây giờ tôi cần submit request."

	Đó mới là agentic behavior.



# 4. Bản chất sâu hơn: Agent = LLM + State + Tools + Decision Loop


	Một cách rất hữu ích để nhớ:
		Agent≈LLM+Tools+State+Decision Loop


	Trong đó:

	① LLM
		Là "bộ não" để:
			hiểu intent
			suy luận
			lập kế hoạch
			lựa chọn tool
			giải thích kết quả

	② Tools

		Là "tay chân".
		Ví dụ:

			search_database()
			call_API()
			send_email()
			create_ticket()
			query_S3()
			execute_SQL()

			LLM bản thân nó không thể tự gửi email hay sửa database.

			Tool mới làm được.



	③ State
		Agent cần nhớ trạng thái của quá trình.

		Ví dụ:

		Goal:
		Đặt chuyến bay Tokyo → Osaka

		State:
			- destination = Osaka
			- date = 2026-10-20
			- passenger = 1
			- budget = ¥30,000
			- flight search = completed
			- selected flight = ANA XXX
			- payment = pending

		Nếu không có state thì rất khó thực hiện một task nhiều bước.



	④ Decision loop	
		
			Đây là phần quan trọng nhất.

			Observe
			   ↓
			Think / Decide
			   ↓
			Act
			   ↓
			Observe result
			   ↓
			Decide again
			   ↓
			Act
			   ↓
			...		
		
	Ví dụ:

		User:
		"Kiểm tra đơn hàng #123 và nếu giao trễ thì gửi email cho khách."

		Agent:

		get_order(123)
				↓
		Result:
		delivery_date = tomorrow

				↓

		Decision:
		Không trễ
				↓
		Không cần send_email()

				↓
		Final response	
				
		
		
	Nếu kết quả khác:

		get_order(123)
			  ↓
		delivery_date = 5 days late
			  ↓
		Decision:
		Need customer notification
			  ↓
		send_email()
			  ↓
		Final response

	Agent không chỉ execute một pipeline cố định. Nó điều chỉnh hành động dựa trên kết quả thực tế.		
			
			
			
# 	5. Đây là điểm phân biệt cực kỳ quan trọng: Workflow vs Agent	
	Hai cái rất dễ nhầm trong AWS exam.	
		
		
|                | Workflow                 | Agent                 |
| -------------- | ------------------------ | --------------------- |
| Logic          | Developer định nghĩa     | LLM có thể quyết định |
| Flow           | Thường cố định           | Dynamic               |
| Tool selection | Code quyết định          | LLM có thể chọn       |
| Branching      | Explicit                 | Có thể dynamic        |
| Predictability | Cao                      | Thấp hơn              |
| Control        | Cao                      | Thấp hơn              |
| Debug          | Dễ hơn                   | Khó hơn               |
| Cost           | Thường thấp hơn          | Có thể cao hơn        |
| Latency        | Predictable              | Có thể biến động      |
| Best for       | Business process rõ ràng | Task cần reasoning    |
		
		
		
	Ví dụ workflow:
		Input
		 ↓
		Validate
		 ↓
		Lambda A
		 ↓
		Lambda B
		 ↓
		Lambda C
		 ↓
		Output

	Không cần Agent.

	Nhưng:

	"Điều tra tại sao khách hàng này bị charge bất thường
	và đề xuất cách xử lý."
		Agent có thể phải:

		search_customer()
			  ↓
		get_transactions()
			  ↓
		detect_anomaly()
			  ↓
		search_policy()
			  ↓
		decide_action()
			  ↓
		create_case()

	Thứ tự và số lượng bước có thể phụ thuộc vào kết quả.

	→ Agent phù hợp hơn.		
			
			
			
			
			
# 	6. Chatbot + RAG cũng chưa chắc là Agent		
			
				
	Đây là một bẫy cực lớn.

	Có hệ thống:
		User
		 ↓
		RAG
		 ↓
		LLM
		 ↓
		Answer

	Nó có thể rất mạnh.			
				
				
	Có:
		embeddings
		vector database
		hybrid search
		reranking
		citations
		grounding
		guardrails

	Nhưng vẫn chưa nhất thiết là Agent.

	Vì nó vẫn chỉ làm:
		Retrieve → Generate → Answer
		Không có autonomous decision/action loop đáng kể.			
				
				
			
# 7. Agent có nhất thiết phải "tự suy nghĩ" không?			
		
	Không nên hiểu Agent theo kiểu:
		"AI tự suy nghĩ như con người."
		Đây là cách hiểu dễ dẫn đến thiết kế sai.		
			
	Trong production, ta quan tâm:
		Goal
		↓
		Decision
		↓
		Tool
		↓
		Observation
		↓
		Decision

	Chứ không quan tâm đến việc LLM "suy nghĩ như người".	
	Thậm chí trong production tốt, không nên giao toàn quyền cho Agent.	
		
		
	Ví dụ:
		Agent
		  ↓
		Request refund
		  ↓
		Policy check
		  ↓
		Human approval
		  ↓
		Execute refund

	Đây chính là human-in-the-loop.		
		
		
		
		
# 	8. Agent không đồng nghĩa với Autonomous	
		
		
	Level 0
	LLM Q&A

	Level 1
	LLM + RAG

	Level 2
	LLM + Tools

	Level 3
	Agent + dynamic tool selection

	Level 4
	Agent + multi-step planning

	Level 5
	Multi-agent / autonomous workflow	
		
		
	Nhưng đây không phải taxonomy chính thức của AWS. Đây chỉ là cách tư duy để hiểu độ phức tạp.	
		
		
	Đặc biệt:
		Nhiều tool ≠ Agent.

	Ví dụ code:
		if intent == "weather":
			get_weather()

		elif intent == "order":
			get_order()

	Đây vẫn có thể chỉ là deterministic application, dù có rất nhiều tools.
	Agentic behavior xuất hiện khi hệ thống có khả năng ra quyết định động dựa trên mục tiêu và trạng thái.

			customization

		Trong đó Amazon Bedrock Agents là managed capability dành cho agentic applications.

	Một kiến trúc điển hình:

		User
		 ↓
		Application
		 ↓
		Amazon Bedrock Agent
		 ↓
		Foundation Model
		 ↓
		┌─────────────────────┐
		│ Tools / Action Group│
		└─────────────────────┘
			   ↓
			 Lambda
			   ↓

	Agent có thể:
		Understand request

			   ↓
		Observe result
			   ↓
		Continue / respond
	
	
# 	10. Action Group chính là một khái niệm phải nhớ

	Trong Bedrock Agents, Action Group là cách expose các hành động mà Agent có thể thực hiện.
	
	Ví dụ:

		Action Group: OrderManagement

		Actions:
		- getOrder()
		- cancelOrder()
		- updateShippingAddress()

		Agent không trực tiếp biết implementation bên dưới.
			
	Nó biết:
		"getOrder can retrieve order information"

	Sau đó backend thực thi action thông qua cơ chế được cấu hình, chẳng hạn Lambda.			
			
	Tư duy kiến trúc:
		LLM
		 ↓
		Agent orchestration
		 ↓
		Action Group
		 ↓
		Lambda
		 ↓
		Business system		
				
			
# 	11. Agent + Knowledge Base cũng rất dễ nhầm
	
	Có thể kết hợp:

		Agent
		 ├── Knowledge Base
		 ├── Order API
		 ├── Customer API
		 └── Ticket API
			
	
	Ví dụ:
		"Khách hàng A yêu cầu hoàn tiền. Hãy kiểm tra policy và đơn hàng rồi xử lý nếu đủ điều kiện."
			
	Agent:

	1. Search Knowledge Base
			↓
	   Refund policy

	2. Query Order API
			↓
	   Order information

	3. Reason
			↓
	   Eligible?

	4. If yes
			↓
	   Refund API

	5. Response

	Đây là sức mạnh thực sự của Agent:
	Knowledge cung cấp information; tools cung cấp capabilities.
		Hai thứ này khác nhau.			
		
		
# 	12. Một nguyên tắc cực quan trọng trong system design	
		
Hãy hỏi:
	"Task này có cần LLM quyết định bước tiếp theo không?"

Nếu không:
	→ dùng deterministic workflow.

Nếu có:
	→ Agent có thể phù hợp.

Ví dụ:
	Không cần Agent
	Upload PDF
	 ↓
	Textract
	 ↓
	Extract fields
	 ↓
	Lambda
	 ↓
	DynamoDB

Flow rõ ràng.
	Agent ở đây có thể chỉ làm hệ thống phức tạp và đắt hơn.

	Có thể cần Agent
	"Điều tra tại sao invoice này bị reject,
	tìm nguyên nhân trong policy + lịch sử giao dịch,
	sau đó đề xuất cách xử lý."

	Task không hoàn toàn predetermined.
	→ Agent có giá trị.		
		
		
		
# 14. Trap: "Agent luôn tốt hơn Workflow"		
		
		
Sai.

Đây là một trong những tư duy nguy hiểm nhất khi thiết kế GenAI.

Nếu workflow:

A → B → C → D

luôn luôn cố định, dùng Agent là thừa.

Agent đưa thêm:

LLM inference cost
latency
nondeterminism
failure modes
observability complexity
security concerns
harder testing

Vì vậy:

	Dùng Agent khi cần dynamic decision-making, không phải vì Agent "xịn hơn".

	Professional-level architecture thường ưu tiên deterministic components ở nơi có thể deterministic, và chỉ dùng LLM/Agent ở nơi thực sự cần flexibility.		
			
			
			
| Keyword trong scenario       | Suy nghĩ                     |
| ---------------------------- | ---------------------------- |
| answer questions             | LLM / RAG                    |
| company documents            | Knowledge Base               |
| retrieve information         | RAG                          |
| cite sources                 | RAG / grounding              |
| execute action               | Tool / Agent                 |
| invoke API                   | Tool / Agent                 |
| update database              | Tool                         |
| dynamically decide           | Agent                        |
| determine next step          | Agent                        |
| multiple tools               | Có thể Agent                 |
| fixed sequence               | Workflow                     |
| predictable execution        | Workflow                     |
| human approval               | Human-in-the-loop            |
| autonomous                   | Agentic                      |
| reduce hallucination         | Grounding / RAG / Guardrails |
| change model behavior        | Fine-tuning                  |
| lower operational complexity | Managed service              |
		
		
		
# 	16. Cô đọng bản chất thành một câu	
		
	Nếu chỉ được nhớ một câu:
		Chatbot chủ yếu trả lời; Agent sử dụng LLM để quyết định và thực hiện các hành động nhằm đạt mục tiêu.

	Hoặc ở mức architecture:

		Agent = Goal + LLM + Tools + State + Dynamic\Decision Loop 

	Và nguyên tắc senior:
		Không phải task nào cũng cần Agent

	Nếu flow biết trước → workflow.
	Nếu cần tìm thông tin → RAG.
	Nếu cần hành động → tools.
	Nếu cần tự quyết định hành động tiếp theo → Agent.
