Lesson 48 -- AIP-C01 --=Amazon Bedrock Knowledge Bases — kiến trúc -//



# Bản chất 

	Amazon Bedrock Knowledge Bases là một managed RAG pipeline: AWS quản lý phần lớn quá trình ingestion → chunking/parsing → embedding → vector storage → retrieval → đưa context cho foundation model.


	AWS hiện cũng có nhiều loại Knowledge Base, bao gồm managed/vector-based KB và các hướng structured data/SQL; vì vậy trong đề Professional, phải nhìn vào kiến trúc và trade-off, không chỉ nhớ tên service.

# 2. Hai pipeline khác nhau — cực kỳ quan trọng

	Một lỗi rất phổ biến khi học RAG là nghĩ:
		User hỏi → Bedrock tìm document → LLM trả lời.

	Không đủ.
	Knowledge Bases có hai lifecycle:



	## A. Ingestion pipeline
		Raw document
			 ↓
		Parse
			 ↓
		Chunk
			 ↓
		Embedding
			 ↓
		Vector Store



	## B. Retrieval / generation pipeline

		User Query
			 ↓
		Query Embedding
			 ↓
		Vector Search
			 ↓
		Top-K chunks
			 ↓
		Reranking (optional)
			 ↓
		Context
			 ↓
		Foundation Model
			 ↓
		Answer
	Đây là distinction rất hay bị AWS dùng để gài đáp án.

# Điểm cần nhớ

	Knowledge Base không lưu document theo nghĩa truyền thống rồi LLM đọc trực tiếp.	
		
	Nó tạo representation để retrieval.	
	
	Ví dụ:
		"Employees must rotate their password every 90 days."	
		
	sau embedding có thể trở thành đại loại:
		[0.021, -0.183, 0.441, ...]
		Vector này biểu diễn semantic meaning của chunk.		
		
		
	

# 4. Chunking — mắt xích cực kỳ quan trọng

	Giả sử PDF có 100 trang.
	Không thể hiệu quả nếu embedding cả PDF thành một vector duy nhất.

	Thay vào đó:
		100-page PDF
			  ↓
		 ┌───────────────┐
		 │ Chunk 1       │
		 │ Chunk 2       │
		 │ Chunk 3       │
		 │ ...           │
		 │ Chunk 500     │
		 └───────────────┘

	Mỗi chunk:
		Chunk
		├── Text
		├── Embedding
		├── Metadata
		└── Source reference


	Tại sao chunking quan trọng?
	
	## Nếu chunk quá lớn:

		Query
		 ↓
		Chunk chứa rất nhiều irrelevant information
		 ↓
		LLM phải xử lý nhiều context
		 ↓
		Cost ↑
		Latency ↑
		Signal/Noise ↓


	

	## Nếu chunk quá nhỏ: 

		Important information
			   ↓
		bị chia thành nhiều chunks
			   ↓
		retrieval có thể chỉ lấy một phần
			   ↓
		context bị thiếu


Cho nên:
	Chunking là retrieval-quality problem, không đơn thuần là storage problem.
	AWS Knowledge Bases cung cấp các cấu hình/customization cho ingestion để điều chỉnh cách dữ liệu được xử lý.


	AWS Knowledge Bases cung cấp các cấu hình/customization cho ingestion để điều chỉnh cách dữ liệu được xử lý.




# 5. Embedding Model

	Sau khi chunk:
		Chunk
		  ↓
		Embedding Model
		  ↓
		Vector

	Ví dụ:
		"How often should employees rotate passwords?"
		↓
		[0.17, -0.04, 0.82, ...]
		Knowledge Bases hỗ trợ embedding models, trong đó có Amazon Titan Text Embeddings V2.


	Điểm cực kỳ quan trọng:
		Document và query phải ở cùng semantic vector space

			Document
			   ↓
			Embedding Model
			   ↓
			Vector D

			Query
			   ↓
			Same/compatible embedding model
			   ↓
			Vector Q



		Sau đó hệ thống có thể tính similarity:
			similarity(Q, D)
			để tìm những chunks gần query nhất.



# 6. Vector Store

	Embedding tạo ra vector nhưng vector phải được lưu ở đâu đó.
	Knowledge Bases có thể sử dụng các vector stores như:
		Amazon OpenSearch Serverless
		Amazon OpenSearch Service
		Amazon Aurora
		Amazon Neptune
		Pinecone
		và các lựa chọn khác tùy kiến trúc/feature hiện hành.


	Một kiến trúc quen thuộc:
		S3
		 ↓
		Bedrock Knowledge Bases
		 ↓
		Embedding
		 ↓
		Amazon OpenSearch Serverless
	

	Hoặc:
		S3
		 ↓
		Bedrock Knowledge Bases
		 ↓
		Embedding
		 ↓
		Aurora PostgreSQL + pgvector


		Embedding
			 ↓
		Vector Database
			 ↓
		OpenSearch
			 ↓
		Aurora PostgreSQL + pgvector

	phải được ghép lại với Knowledge Bases.



# 7. Query-time — chuyện gì xảy ra khi user hỏi?


 cơ bản:

	User Query
		↓
	Embedding Model
		↓
	Query Vector
		↓
	Vector Search
		↓
	Relevant Chunks

Ví dụ:
	Top-K = 5
	Chunk #183  similarity 0.91
	Chunk #092  similarity 0.89
	Chunk #411  similarity 0.86
	Chunk #205  similarity 0.84
	Chunk #377  similarity 0.82

	Sau đó có thể sử dụng reranking để cải thiện thứ tự kết quả retrieval. AWS Knowledge Bases hỗ trợ reranking models trong quá trình query.






# 8. Retrieve vs RetrieveAndGenerate


	Đây là phần rất quan trọng cho AIP-C01.
	Knowledge Bases cung cấp ít nhất hai abstraction quan trọng:

		| API                   | Làm gì?                |
		| --------------------- | ---------------------- |
		| `Retrieve`            | Chỉ retrieval          |
		| `RetrieveAndGenerate` | Retrieval + generation |

	AWS xác nhận Retrieve trả về source chunks/images liên quan, còn RetrieveAndGenerate kết hợp retrieval với model invocation để tạo natural-language response.


	## Retrieve
		User Query
			↓
		Knowledge Base
			↓
		Relevant chunks
			↓
		Application

		Application tự quyết định làm gì tiếp.

	Ví dụ:
		Lambda
		  ↓
		Retrieve
		  ↓
		Build custom prompt
		  ↓
		InvokeModel
		  ↓
		Claude / Nova / ...

	Điều này cho bạn control cao hơn.




	## RetrieveAndGenerate 
		User Query
			↓
		Knowledge Base
			↓
		Retrieve
			↓
		Context augmentation
			↓
		Foundation Model
			↓
		Answer

	AWS quản lý nhiều phần của RAG flow.

	Tư duy thi:
		Retrieve = tôi muốn kiểm soát retrieval/application logic.
		RetrieveAndGenerate = tôi muốn managed RAG flow nhanh hơn.




# 9. Knowledge Bases KHÔNG phải Foundation Model


	Đây là một distinction phải thuộc.
		Knowledge Base
			  ≠

# 10. Knowledge Base ≠ Fine-tuning


	Không cần retrain model.

	AWS cũng nhấn mạnh Knowledge Bases giúp đưa proprietary data vào ứng dụng mà không cần continually train model trên private data.

# 12. Managed Knowledge Base vs tự xây RAG

	Đây là trade-off mà Professional exam rất thích.

|                    | Bedrock Knowledge Bases | Custom RAG        |
| ------------------ | ----------------------- | ----------------- |
| Ingestion          | Managed                 | Tự xây            |
| Chunking           | Managed/configurable    | Tự implement      |
| Embedding          | Managed integration     | Tự gọi model      |
| Vector DB          | AWS/integrated options  | Tự quản lý        |
| Retrieval          | Managed                 | Tự code           |
| Reranking          | Có hỗ trợ               | Tự tích hợp       |
| Development speed  | **Nhanh**               | Chậm              |
| Control            | Trung bình/cao tùy mode | **Rất cao**       |
| Operational burden | **Thấp hơn**            | Cao               |
| Custom pipeline    | Hạn chế hơn             | **Rất linh hoạt** |


	AWS hiện khuyến nghị Managed Knowledge Base cho optimized retrieval accuracy và managed experience. Đồng thời customer-managed KB vẫn phù hợp khi cần kiểm soát pipeline/vector store/configuration sâu hơn.

# 	14. Điểm AWS hay gài trong đề			
				
				
	## Trap 1 — "Private data → Fine-tuning"

		Nghe có vẻ đúng nhưng không mặc định đúng.
		Nếu requirement là:
			"Company policies change frequently and answers must reflect the latest documents."
			→ RAG / Knowledge Base thường phù hợp hơn fine-tuning.			
							
							
						
						
				
				
	## 	Trap 2 — "Knowledge Base tự biết dữ liệu mới"		
				
	Không nên nghĩ vậy.
		Data source thay đổi thì ingestion/sync phải cập nhật index. AWS mô tả rõ việc sync chuyển raw data thành embeddings để dữ liệu có thể được query.				
					
		S3 updated
		   ↓
		Knowledge Base
		   ↓
		Sync
		   ↓
		New embeddings/index					
							
				
				
				
	## Trap 3 — "Vector DB là Knowledge Base"			
				
				
		Sai.
			Knowledge Base
			 ├── Data source
			 ├── Parsing
			 ├── Chunking
			 ├── Embedding
			 ├── Vector store
			 ├── Retrieval
			 └── Generation integration

		Vector DB chỉ là một component.				
						
						
						
				
				
	## 	Trap 4 — "Retrieve và RetrieveAndGenerate giống nhau"	
				
		Sai.

		Retrieve
			= retrieval only

		RetrieveAndGenerate
			= retrieval + generation				
						
						
				
				
	## 	Trap 5 — "Vector search luôn đủ"	
		Không nhất thiết.

		Nếu retrieval quality chưa tốt:
			Query
			 ↓
			Vector Search
			 ↓
			Bad Top-K
			 ↓
			LLM
			 ↓
			Confident wrong answer

		Có thể cần:
			Better chunking
			+
			Metadata filtering
			+
			Hybrid search
			+
			Reranking
			+
			Better embedding

		Professional exam thường kiểm tra retrieval quality, chứ không chỉ hỏi “Knowledge Bases dùng service nào”.


# 15. Structured data là một nhánh khác

	Đừng nhét tất cả vào vector DB.

		Ví dụ:

		Question:
			"Doanh thu tháng 8 của chi nhánh Tokyo là bao nhiêu?"

		Đây là dữ liệu có cấu trúc:
			sales
			├── date
			├── branch
			├── product
			└── revenue

		Knowledge Bases hiện hỗ trợ structured data stores và có thể chuyển natural-language query thành SQL để truy vấn dữ liệu thay vì bắt buộc vectorize mọi thứ. Các nguồn được hỗ trợ gồm Amazon Redshift và AWS Glue Data Catalog/Lake Formation tùy cấu hình/Region.


		Tư duy:

		Unstructured
			PDF / DOCX / HTML
					↓
			Embedding
					↓
			Vector Retrieval


		Structured
			SQL tables
					↓
			Natural Language → SQL
					↓
			Database Query

		Đây là điểm rất đáng nhớ cho AIP-C01.

# 17. Từ khóa AIP-C01


| Keyword trong đề              | Nghĩ ngay đến                                  |
| ----------------------------- | ---------------------------------------------- |
| Private company documents     | RAG / Knowledge Base                           |
| Frequently changing data      | RAG                                            |
| Avoid model retraining        | Knowledge Base                                 |
| Semantic search               | Embedding + Vector Store                       |
| Chunking                      | Ingestion                                      |
| Embedding model               | Text → Vector                                  |
| Vector store                  | OpenSearch / Aurora / ...                      |
| Top-K                         | Retrieval                                      |
| Poor retrieval quality        | Chunking / embedding / retrieval tuning        |
| Reranking                     | Improve relevance of retrieved results         |
| `Retrieve`                    | Retrieval only                                 |
| `RetrieveAndGenerate`         | RAG + generation                               |
| Agent needs company knowledge | Agent + Knowledge Base                         |
| Structured business data      | SQL/structured KB path                         |
| Latest information            | Retrieve current source data, not model memory |




# 18. Cách AWS ra đề

	Một scenario kiểu Professional có thể nói:
		Một công ty có hàng triệu tài liệu nội bộ. Nhân viên cần hỏi đáp về policy. Documents được cập nhật hàng ngày. Công ty muốn tránh retraining foundation model và muốn giảm operational overhead. Hệ thống phải cung cấp source citations.



	Đừng nhìn thấy:
		"millions of documents"
		rồi chọn ngay OpenSearch.

	Hãy parse requirement:


		Private data
			  ↓
		RAG

		Frequently updated
			  ↓
		No fine-tuning

		Reduce operational overhead
			  ↓
		Managed Knowledge Base

		Need source attribution
			  ↓
		Knowledge Base retrieval/generation + citations


	Đáp án tốt thường là đáp án thỏa toàn bộ constraint, không phải đáp án “có vẻ kỹ thuật nhất”.

	Đây chính là tư duy Professional-level:
		Requirement → architectural constraint → service choice → trade-off

	chứ không phải:
		Keyword → AWS service.
