Lesson 210 -- Functional Fallback & Recovery Pattern -//



# ⚙️ 1. Vấn đề của try/catch trong hệ thống lớn

Trong hệ thống thực tế (ví dụ: thanh toán, email, ETL):


	Hầu như tất cả các call đều có thể fail.
	Bạn cần fallback (chuyển hướng sang phương án dự phòng) — ví dụ:
		Payment fail → thử backup provider.
		Email service down → gửi qua queue để retry sau.

	Nếu ta dùng try/catch khắp nơi, code sẽ trở thành:

try {
    payment.charge();
} catch (Exception e1) {
    try {
        backupPayment.charge();
    } catch (Exception e2) {
        logger.error("Both providers failed");
    }
}


→ Vô cùng rối, khó test, khó compose, và tệ hơn: logic resilience bị lẫn vào logic nghiệp vụ.

Functional approach giúp ta tách biệt hoàn toàn hai tầng này.



# 🧩 2. Giới thiệu Try<T> Monad (hoặc Either<Error, T>)

	Try<T> là một container biểu diễn kết quả có thể thành công hoặc thất bại, thay thế hoàn toàn cho try/catch.

	Giống như Optional<T>, nhưng có thêm error info:

	Try<T> = Success<T> | Failure<Throwable>

	Ví dụ minh họa đơn giản:


class Try<T> {
    private final T value;
    private final Throwable error;

    private Try(T value, Throwable error) {
        this.value = value;
        this.error = error;
    }

    public static <T> Try<T> of(Supplier<T> fn) {
        try {
            return new Try<>(fn.get(), null);
        } catch (Throwable t) {
            return new Try<>(null, t);
        }
    }

    public boolean isSuccess() { return error == null; }
    public T getOrElse(T fallback) { return isSuccess() ? value : fallback; }
    public Try<T> recoverWith(Supplier<T> fallbackFn) {
        return isSuccess() ? this : Try.of(fallbackFn);
    }
}


	## Bây giờ, không cần try/catch, ta viết: 

var result = Try.of(() -> payment.charge())
                .recoverWith(() -> backupPayment.charge());



	## 💡 Điểm mạnh: 

		Không throw exception.
		Dễ chain logic fallback.
		Có thể log, map, transform kết quả như stream.



# 🧠 3. Either<Error, Result> — mô hình Monad mạnh hơn Try

	Nếu bạn muốn phân biệt lỗi có loại cụ thể (ví dụ: network fail, validation fail, provider fail), ta dùng Either<L, R>.


	Either<Error, PaymentResponse> result = payment.charge();

		Left = lỗi
		Right = kết quả

	Sau đó:
		result.orElse(() -> backupPayment.charge());

	Cách này an toàn hơn, vì error type là kiểu cụ thể (có thể sealed interface trong Java 17+).



# 🔗 4. Policy chaining: withRetry().recoverWith(fallback)
	Bây giờ ta kết hợp bài trước (Resilience composition) với fallback functional.

Supplier<CompletableFuture<String>> resilient =
    withRetry(3)
    .andThen(withTimeout(Duration.ofSeconds(2)))
    .apply(() -> callPaymentProvider())
    .recoverWith(() -> callBackupProvider());

	→ Khi callPaymentProvider() thất bại sau retry, fallback tự động chạy — không try/catch, không annotation.


# 🏢 5. Ứng dụng thực tế: ETL và Payment Pipeline

	ETL Pipelines:
		Trong pipeline data transformation:

		Một job có thể fail ở một stage (ví dụ parse JSON).
		Dùng Try hoặc Either để fallback sang parsing “lenient” mode.

	Kết quả: pipeline vẫn chạy tiếp, không crash toàn bộ.


	## Payment Orchestration:
Try<PaymentResult> payment =
    Try.of(() -> stripe.charge(request))
       .recoverWith(() -> paypal.charge(request))
       .recoverWith(() -> square.charge(request));

	Ta có thể chain vô hạn provider fallback.
	Và toàn bộ pipeline bất biến, test dễ dàng:
		assertTrue(payment.isSuccess());

	Không có try/catch, không throw exception — code pure functional.



# 🧰 6. Kết hợp Try + Logging + Metrics
	Bạn có thể kết hợp log hoặc metrics mà vẫn giữ functional purity:

Try.of(() -> stripe.charge(request))
   .peekSuccess(r -> metrics.increment("payment.success"))
   .peekFailure(e -> metrics.increment("payment.fail"))
   .recoverWith(() -> paypal.charge(request));

	→ Xử lý observability ngay trong pipeline, không phá vỡ purity.


# 💡 7. So sánh với cách truyền thống

| Mô hình     | Truyền thống        | Functional Monad                         |
| ----------- | ------------------- | ---------------------------------------- |
| Cấu trúc    | try/catch lồng nhau | Chain `.recoverWith()`                   |
| Testability | Khó mock, throw     | Pure function, dễ test                   |
| Logging     | Rải rác             | Centralized `.peekFailure()`             |
| Compose     | Không thể           | `.map()`, `.flatMap()`, `.recoverWith()` |
| Readability | Rối                 | Rõ pipeline                              |



# 🔮 8. Triết lý cuối cùng

Resilience thật sự không nằm ở framework, mà nằm ở cách bạn tổ chức luồng xử lý lỗi một cách có kiểm soát.
Functional fallback cho phép:

	Cấu trúc lỗi thành dữ liệu.
	Compose logic như pipeline.
	Không rơi vào callback hell hay AOP magic.
